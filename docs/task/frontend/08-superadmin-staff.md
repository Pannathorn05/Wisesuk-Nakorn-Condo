## Section map จาก prototype

**หน้าหลัก (ภาพ 53)** — อยู่ใน `AdminShell` เดิม (sidebar + เนื้อหา) ที่ทำไว้แล้วใน FE-30

2. ปุ่ม **"เพิ่มผู้ดูแล"** (primary) ชิดขวา อยู่เหนือตาราง
3. ตาราง 4 คอลัมน์:
   | คอลัมน์ | เนื้อหา |
   |---|---|
   | ผู้ดูแล | ชื่อ-นามสกุล (ตัวหนา) + อีเมลบรรทัดล่าง (ตัวเล็ก สีจาง) |
   | บทบาท | superadmin = **badge pill สีน้ำตาลเข้ม ตัวอักษรขาว** "Superadmin" · admin = ข้อความธรรมดา "Admin" |
   | สิทธิ์ดูแลสาขา | ชื่อสาขาที่ดูแล · superadmin = "ทุกสาขา" |
   | จัดการ | ลิงก์ "แก้ไข" + ไอคอนถังขยะสีแดง — **แถว superadmin มีแค่ "แก้ไข" ไม่มีไอคอนลบ** |

**Modal เพิ่ม/แก้ไข (ภาพ 54/55)** — โครงเดียวกัน ต่างแค่หัวข้อและค่าที่เติมไว้
1. หัว modal: "เพิ่มผู้ดูแลใหม่" / "แก้ไขผู้ดูแล" + ปุ่มกากบาทปิดมุมขวาบน
2. แถวคู่: **ชื่อ** | **นามสกุล**
3. แถวคู่: **อีเมล** | **เบอร์โทรศัพท์**
4. กล่อง **"สิทธิ์ดูแลสาขา"** — รายการสาขาพร้อม checkbox (ในภาพมี 3 สาขา)
   ใต้กล่องมีข้อความเล็ก: *"เลือกได้หลายสาขา — Admin จะเข้าถึงเฉพาะสาขาที่ได้รับสิทธิ์"* ← **ขัดกับ backend ดู Gap ข้อแรก**
5. ปุ่มล่างขวา: **ยกเลิก** (secondary) + **บันทึก** (primary)
6. **ไม่มีช่องรหัสผ่านในฟอร์ม** — ตรงกับ backend ที่ตั้งรหัสตั้งต้นให้เอง (ดูหัวข้อ API)

## API จริงที่มีอยู่แล้ว (`docs/openapi.yaml` + curl จริงกับ backend ที่รันอยู่)

- **`GET /api/v1/superadmin/staff`** → `{ data: User[] }` — รายชื่อผู้ดูแลทั้งหมด **รวมตัว superadmin เอง**
  (curl จริงได้ 4 แถว: superadmin 1 + admin 3 ตรงกับตารางในภาพ 53)
  `User` มี `id`, `first_name`, `last_name`, `email`, `phone`, `role`, `branch_id` (**nullable — superadmin เป็น null**), `is_active`
- **`GET /api/v1/superadmin/branches`** → `Branch[]` **รวมสาขาที่ปิดใช้งาน** — ใช้เติมรายการสาขาในกล่อง "สิทธิ์ดูแลสาขา"
  และใช้แปลง `branch_id` → ชื่อสาขาในคอลัมน์ที่ 3 ของตาราง
- **`POST /api/v1/superadmin/staff`** — `CreateStaffRequest {email, first_name, last_name, phone, branch_id}` ทั้ง 5 ช่อง **required**
  - **ไม่รับรหัสผ่าน** — ระบบตั้งรหัสตั้งต้นจาก env `STAFF_DEFAULT_PASSWORD` แล้วตั้ง `must_change_password = true` ให้เอง (ตรงกับ modal ที่ไม่มีช่องรหัสผ่าน ✓)
  - สำเร็จ `201` คืน `User` · `422 validation_failed` พร้อม `error.fields` (เช่น `email`: "อีเมลนี้ถูกใช้งานแล้ว")
- **`PUT /api/v1/superadmin/staff/{userID}`** — `UpdateStaffRequest {first_name?, last_name?, phone?, branch_id?, is_active?, password?}` ทุกช่อง optional
  - `branch_id` **บังคับเมื่อเป้าหมาย role = admin และห้ามส่งเมื่อเป้าหมายเป็น superadmin**
  - `400` "ระงับบัญชีตัวเองไม่ได้" · `404` "ไม่พบ หรือเป้าหมายเป็นสมาชิกไม่ใช่ผู้ดูแล" · `422` (อีเมลซ้ำ/สาขาซ้ำ)
- **`DELETE /api/v1/superadmin/staff/{userID}`** — soft delete · `204` สำเร็จ · **`400` "ลบบัญชีตัวเองไม่ได้"**
  (สอดคล้องกับภาพ 53 ที่แถว superadmin ไม่มีไอคอนถังขยะ)
- ทุก endpoint อยู่หลัง guard `RequireRole roles={["superadmin"]}` ที่ทำไว้แล้วใน FE-28 — ฝั่ง backend ก็เช็ค role เองอีกชั้น

## Gap ที่เจอ — ต้องตัดสินใจก่อน implement ไม่ใช่เดาเอง

- 🔴 **[สำคัญที่สุด] prototype ให้เลือกหลายสาขา แต่ backend รองรับสาขาเดียวเท่านั้น**
  ภาพ 54/55 เป็น checkbox หลายช่อง + เขียนกำกับว่า *"เลือกได้หลายสาขา"* แต่ `CreateStaffRequest.branch_id` /
  `UpdateStaffRequest.branch_id` / `User.branch_id` เป็น **string เดี่ยว** และ spec เขียนไว้ตรง ๆ ว่า
  *"สาขาที่รับผิดชอบ **เลือกได้สาขาเดียว** เลือกสาขาที่มีผู้ดูแลอยู่แล้วจะได้ 422 เพราะ**หนึ่งสาขามีผู้ดูแลได้คนเดียว**"*
  **ยืนยันด้วย curl จริงแล้ว**: `POST` ด้วย `branch_id: brn-001` (ที่มีผู้ดูแลแล้ว) ได้ `422` พร้อม
  `fields.branch_id: "สาขานี้มีผู้ดูแลอยู่แล้ว หนึ่งสาขามีผู้ดูแลได้คนเดียว"`
  → ตาม hard rule ข้อ 4 (backend เป็น source of truth ด้าน API ต้อง adapt frontend ตาม backend)
  **แนะนำ: เปลี่ยนเป็นเลือกได้สาขาเดียว (radio) + แก้ข้อความใต้กล่องให้ตรงความจริง + disable สาขาที่มีผู้ดูแลอยู่แล้ว
  พร้อมเขียนกำกับว่าใครดูแลอยู่** — แต่ขัดกับ prototype ต้องให้ทีมเคาะก่อน (ทางเลือกอื่นคือให้ backend
  เปลี่ยนเป็น many-to-many ซึ่งอยู่นอกขอบเขต frontend รอบนี้)
- 🔴 **ตอนนี้ทุกสาขามีผู้ดูแลครบแล้ว (3/3)** — curl จริงพบ admin ครบทั้ง brn-001/002/003
  แปลว่า flow "เพิ่มผู้ดูแล" จะ**ล้มเหลวด้วย 422 เสมอ**จนกว่าจะมีสาขาใหม่หรือย้าย/ลบผู้ดูแลเดิมออกก่อน
  → ต้องออกแบบ UI ให้บอกผู้ใช้ชัดว่า "ไม่มีสาขาว่างให้มอบหมาย" ตั้งแต่ก่อนกดบันทึก (ไม่ใช่ปล่อยให้กดแล้วเจอ error)
  และตอนเทสต้องเตรียมข้อมูลเอง (เช่นลบ/ย้าย admin สักคนก่อน) ไม่งั้นเทส happy path ไม่ได้เลย
- **แถว superadmin ในตารางมีปุ่ม "แก้ไข" ด้วย** แต่ `UpdateStaffRequest` ห้ามส่ง `branch_id` เมื่อเป้าหมายเป็น superadmin
  → ตอนเปิด modal แก้ไข superadmin ต้อง**ซ่อน/ปิดกล่องเลือกสาขา** (แก้ได้แค่ชื่อ/นามสกุล/เบอร์โทร) ไม่งั้นจะยิงผิดสัญญา
- **ภาพ 53 ไม่มี subtext ใต้หัวข้อ แต่ภาพ 54/55 มี** ("เพิ่ม/แก้ไข บัญชี Admin สาขา และกำหนดสิทธิ์ดูแลสาขา")
  น่าจะเป็นความไม่สม่ำเสมอของ prototype เอง → **แนะนำใส่ subtext ทุกกรณี** (ให้หน้าคงที่ไม่กระตุกตอนเปิด/ปิด modal) ต้องเคาะ
- **`is_active` และ `password` ส่งได้ใน `PUT` แต่ไม่มีใน modal ของ prototype** — รอบนี้**ไม่ต้องทำ** (ทำตาม prototype)
  บันทึกไว้ว่าถ้าอยากได้ฟีเจอร์ "ระงับบัญชี" / "รีเซ็ตรหัสผ่านให้ผู้ดูแล" ต้องแตก task เพิ่ม (API พร้อมแล้ว)
- 🔴 **`docs/openapi.yaml` เขียนว่า `DELETE` เป็น "soft delete" แต่โค้ด backend จริงลบถาวร**
  `backend/internal/modules/account/repository.go` → `DELETE FROM users WHERE id = $1 AND role = 'admin'`
  (ไม่ได้ตั้ง flag ใด ๆ) แปลว่า **แถวหายจากฐานข้อมูลจริง กู้คืนไม่ได้** และ `RevokeAllRefreshTokens` ถูกเรียกต่อท้าย
  → ข้อความยืนยันก่อนลบต้องบอกว่า "ลบถาวร" ตามความจริง (ถ้าเขียนว่าแค่ปิดการใช้งานจะหลอกผู้ใช้)
  **ควรแจ้งทีม backend ให้แก้ description ใน spec ให้ตรงกับโค้ด** (เป็นเรื่องของ backend/เอกสาร ไม่ใช่ frontend)
  ผลข้างเคียงที่ดีคือ: ถ้าเผลอลบบัญชี seed ไป **รันสคริปต์ seed ซ้ำจะได้บัญชีนั้นกลับมา** (seed ใช้ `ON CONFLICT (email) DO NOTHING` — พอแถวถูกลบจริงก็ไม่ conflict แล้ว)
- **prototype ไม่มีภาพ confirm dialog ก่อนลบ** แต่การลบเป็น action ที่ย้อนกลับไม่ได้จากฝั่ง UI
  → **แนะนำใส่ confirm** (ใช้รูปแบบ modal เดียวกับที่มีอยู่) ต้องเคาะว่าทีมโอเคกับการเพิ่มที่ prototype ไม่มี

**FE-35 · API layer + ตารางรายชื่อผู้ดูแล**
- ทำ: `api/superadminApi.jsx` (`listStaff`, `createStaff`, `updateStaff`, `deleteStaff`, `listAllBranches`) ตาม pattern `adminApi`/`branchApi` เดิม · hook `useStaffList` (+ `useAllBranches` สำหรับ map `branch_id` → ชื่อสาขา และเติมตัวเลือกใน modal) · หน้า `/superadmin/staff` แทน `ComingSoonPage` — หัวข้อ + ปุ่ม "เพิ่มผู้ดูแล" + ตาราง 4 คอลัมน์ตาม section map (badge "Superadmin", "ทุกสาขา", ปุ่มลบไม่ขึ้นในแถว superadmin)
- ขึ้นกับ: FE-30 (AdminShell), FE-28 (guard)
- DoD: E2E ครบ 4 สถานะ — loading = skeleton แถวตาราง, error = ข้อความ + ปุ่มลองใหม่, empty = ไม่มีผู้ดูแล เห็นข้อความชัดเจน, success = จำนวนแถว/ชื่อ/อีเมล/บทบาท/สาขา ตรงกับ `GET /superadmin/staff` จริง (เทียบ curl) · แถว superadmin แสดง "ทุกสาขา" และไม่มีไอคอนลบ

**FE-36 · Modal "เพิ่มผู้ดูแลใหม่" — `POST /superadmin/staff`**
- ทำ: modal ตามภาพ 54 (ชื่อ/นามสกุล/อีเมล/เบอร์โทร + กล่องเลือกสาขาตามที่เคาะใน Gap + ยกเลิก/บันทึก) · validate ฝั่ง client ก่อนยิงให้ตรงกฎ backend (ทุกช่อง required, อีเมล format, `phone` ตรง `^[0-9]{9,10}$`, ต้องเลือกสาขา) — reuse `authValidation` เดิมได้บางส่วน · สำเร็จปิด modal + refresh ตาราง
- ขึ้นกับ: FE-35
- DoD: E2E ครบ idle/submitting (ปุ่ม disabled กันกดซ้ำ)/error/success · **รวม 422 ทั้ง 2 เคสจริง: อีเมลซ้ำ → error ใต้ช่องอีเมล, สาขามีผู้ดูแลแล้ว → error ใต้กล่องสาขา** (ใช้ `error.fields` จาก backend ตรง ๆ ไม่เขียนข้อความเอง) · ถ้าไม่มีสาขาว่างเลย ต้องบอกผู้ใช้ตั้งแต่ก่อนกดบันทึก (ตาม Gap)

**FE-37 · Modal "แก้ไขผู้ดูแล" — `PUT /superadmin/staff/{userID}`**
- ทำ: modal เดียวกับ FE-36 แต่เติมค่าเดิมจากแถวที่กด (ภาพ 55) · **เป้าหมายเป็น superadmin ต้องซ่อน/ปิดกล่องเลือกสาขาและไม่ส่ง `branch_id`** ตาม Gap · ส่งเฉพาะฟิลด์ที่แก้จริง (ทุกช่อง optional)
- ขึ้นกับ: FE-36
- DoD: E2E ครบ idle/submitting/error/success · **รวม 400 "ระงับบัญชีตัวเองไม่ได้", 404 "ไม่พบ หรือเป้าหมายเป็นสมาชิกไม่ใช่ผู้ดูแล", 422 (อีเมล/สาขาซ้ำ) แสดงเป็นภาษาคนจาก backend** · แก้ superadmin แล้วไม่มี `branch_id` หลุดไปใน payload (ตรวจจาก network จริง) · ตารางอัปเดตทันทีหลังบันทึก

**FE-38 · ลบผู้ดูแล — `DELETE /superadmin/staff/{userID}`**
- ทำ: ไอคอนถังขยะในแถว admin → confirm ก่อนลบ (ตาม Gap; ข้อความห้ามเขียนว่า "ลบถาวร" เพราะเป็น soft delete) → ยิง DELETE → refresh ตาราง
- ขึ้นกับ: FE-35
- DoD: E2E ครบ · **รวม 400 "ลบบัญชีตัวเองไม่ได้" แสดงเป็นภาษาคน** (ถึงแม้ UI จะซ่อนปุ่มลบของ superadmin ไว้แล้ว ก็ต้องกัน error จาก backend ให้ครบ) · ยกเลิกใน confirm แล้วต้องไม่มี request ถูกยิง · ลบสำเร็จแล้วแถวหายจากตารางจริง
