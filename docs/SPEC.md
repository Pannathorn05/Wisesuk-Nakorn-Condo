# SPEC ระบบจองห้องพักวิเศษสุขนครคอนโด

ที่มาของเอกสาร
- เขียนย้อนจากโค้ดจริงทั้ง repo ณ 2026-09-24 ทั้ง backend, frontend, seed และ docker
- ทุกข้อเขียนในรูป "ทำแบบนี้ → ได้ผลแบบนี้" ตรวจได้ด้วยการกดหน้าเว็บ ยิงระบบ หรือดูฐานข้อมูล
- เอกสารนี้ไม่มีรายละเอียดระดับ API (ชื่อ endpoint, HTTP status, รูปแบบ JSON) ส่วนนั้นอยู่ใน docs/openapi.yaml
- คำว่า "ข้อมูลไม่ถูกต้อง", "ไม่พบข้อมูล", "ไม่มีสิทธิ์" ฯลฯ ในเอกสารนี้ แปลงเป็นรหัส error ตามที่ AC-21 กำหนด
- งานที่ต้องทำต่อจากเอกสารนี้อยู่ใน docs/Task-BE/

ป้ายกำกับ
- [ยังไม่ implement] ตกลงกันว่าจะทำ แต่โค้ดยังไม่มี ห้ามเขียนเทสยืนยันจนกว่าจะทำจริง
- [ช่องว่าง] โค้ดทำแบบนี้อยู่จริง แต่น่าจะไม่ได้ตั้งใจ หรือขัดกฎใน AGENTS.md หรือขัดกับเอกสาร ต้องให้ human ตัดสินว่าจะแก้หรือยอมรับ
- [ยอมรับความเสี่ยง] ตัดสินใจแล้วว่ารับได้
- [ยังไม่ยืนยัน] อนุมานจากการอ่านโค้ด ยังไม่ได้รันเทสยืนยัน
- บรรทัด "เทสที่มี" ท้ายแต่ละ AC บอกไฟล์เทสที่คุมข้อนั้นอยู่ ถ้าเขียนว่า "ยังไม่มีเทส" แปลว่าทดสอบได้แต่ยังไม่มีคนเขียน

## ส่วนประกอบของระบบ
- backend เขียนด้วย Go ใช้ฐานข้อมูล PostgreSQL 16 รันด้วย Docker Compose ที่พอร์ต 8080
- ฐานข้อมูลและ pgAdmin เปิดให้เข้าได้จากเครื่องตัวเองเท่านั้น
- ตารางในฐานข้อมูลถูกสร้างและอัปเดตเองทุกครั้งที่ backend เริ่มทำงาน
- ข้อมูลตั้งต้น (สาขา ห้อง บัญชี) ใส่ด้วยคำสั่ง seed แยกต่างหาก
- frontend เป็น React (Create React App) รันที่พอร์ต 3000 แยกจาก docker และคุยกับ backend ผ่าน URL ที่ตั้งใน env
- รูปสาขาและห้องที่แอดมินอัปโหลดถูกเก็บเป็นไฟล์ในฐานข้อมูล ส่วนสลิปโอนเงินและรูปเดโมจาก seed เก็บเป็นไฟล์บนดิสก์

## ผู้ใช้
- Guest ดูสาขา ดูห้อง ค้นหาห้องว่างตามวันที่ ราคา ประเภท และสมัครสมาชิกได้โดยไม่ต้องล็อกอิน
- Member จองห้องรายวันหรือรายเดือน แจ้งชำระเงินพร้อมสลิป ดูและยกเลิกการจองของตัวเอง รับแจ้งเตือน ล็อกอินด้วยอีเมลและรหัสผ่าน หรือด้วย Google/Facebook (ดู AC-24)
  - ฝั่งหน้าเว็บยังไม่มีหน้าใดของ Member นอกจากหน้าเข้าสู่ระบบและหน้าสมัครสมาชิก (ดู AC-31)
- Admin จัดการห้องและรายละเอียดสาขา อนุมัติ ปฏิเสธ ยกเลิกการจอง นัดทำสัญญา ดูแดชบอร์ด ประวัติการใช้งาน และรายชื่อสมาชิก ได้เฉพาะสาขาที่ผูกอยู่ 1 สาขา (ดู AC-4)
  - ฝั่งหน้าเว็บมีแค่หน้าเข้าสู่ระบบ แล้วตกไปหน้าที่ยังไม่ได้ทำ
- Super Admin ทำได้ทุกอย่างที่ Admin ทำได้ในทุกสาขา และเพิ่ม แก้ ระงับ ลบบัญชีผู้ดูแลได้ (ดู AC-18)
  - ฝั่งหน้าเว็บมีแดชบอร์ดกับหน้าจัดการผู้ดูแล
- กฎสิทธิ์ที่ฐานข้อมูลบังคับเอง
  - admin ต้องผูกกับสาขาเสมอ และบทบาทอื่นห้ามผูกสาขา
  - หนึ่งสาขามี admin ที่ยังไม่ถูกลบได้คนเดียว
  - ทั้งระบบมี super admin ได้คนเดียว
- ระบบเชื่อ token แค่ว่าผู้ใช้เป็นใคร ส่วนบทบาท สาขา และสถานะบัญชีอ่านจากฐานข้อมูลทุกครั้ง การลบ ระงับ หรือย้ายสาขาจึงมีผลทันที (ดู AC-3, AC-4)

## สิ่งที่ระบบยังไม่มี
- สร้าง ลบ หรือเปิดปิดสาขา ทำได้แค่แก้รายละเอียดสาขาที่มาจาก seed ส่วนการปิดสาขาต้องแก้ในฐานข้อมูลตรง
- จัดการประเภทห้องและรายการสิ่งอำนวยความสะดวกกลาง ใส่ได้ทาง seed เท่านั้น แอดมินทำได้แค่เลือกจากรายการที่มี
- สร้าง Super Admin ผ่านระบบ ทำได้ทาง seed เท่านั้น
- ชำระเงินออนไลน์หรือตัดบัตร ใช้วิธีโอนเงินแล้วแนบสลิปให้แอดมินตรวจแทน
- คืนเงิน ค่าปรับ ใบเสร็จ ใบกำกับภาษี
- ยืนยันอีเมล และเปลี่ยนอีเมล
- ระงับหรือลบบัญชี member ทำได้เฉพาะบัญชีผู้ดูแล (ดู AC-18)
- ส่งอีเมลหรือ SMS ไม่มีเลยสักจุด แจ้งเตือนทั้งหมดอยู่ในกล่องแจ้งเตือนของระบบ
- member รีเซ็ตรหัสผ่านเองเมื่อลืม [ยังไม่ implement] (ดู AC-23) ตอนนี้ super admin รีเซ็ตให้ได้เฉพาะบัญชีผู้ดูแล
- จำกัดความถี่ของการสมัคร การต่ออายุ token และการล็อกอินผ่าน Google/Facebook มีจำกัดเฉพาะการล็อกอินด้วยรหัสผ่าน (ดู AC-2)
- จบสัญญาหรือเช็คเอาต์ แอดมินต้องเปลี่ยนสถานะห้องเองแทน
- บังคับให้ผู้ดูแลที่ได้รหัสตั้งต้นต้องเปลี่ยนรหัสก่อนใช้งาน ระบบแค่ปักธงไว้ ทั้ง backend และหน้าเว็บยังไม่บังคับ (ดู AC-37)
- หมวดของสถานที่ใกล้เคียงเป็นข้อความอิสระ ไม่ได้จำกัดค่า
- หน้าเว็บที่ยังไม่มี แม้ระบบหลังบ้านรองรับแล้ว
  - หน้ารายละเอียดห้อง
  - ฟอร์มจอง แจ้งชำระเงิน ประวัติการจอง ยกเลิกการจอง
  - โปรไฟล์ เปลี่ยนรหัสผ่าน กระดิ่งแจ้งเตือน
  - ปุ่มล็อกอินด้วย Google/Facebook และหน้ารับผลกลับมา
  - ทุกหน้าของ Admin สาขา
  - เมนูจัดการสาขา และหน้าประวัติการใช้งานของ Super Admin
  - การต่ออายุการล็อกอินอัตโนมัติ

## Acceptance Criteria — ระบบหลังบ้าน

AC-1: สมัครสมาชิกได้ และได้สิทธิ์ member เสมอ
- สมัครด้วยอีเมลใหม่และข้อมูลครบ → สำเร็จ ได้สถานะล็อกอินทันทีในบทบาท member และมีบันทึกการสมัครในประวัติการใช้งาน
- ข้อมูลที่รับมีแค่อีเมล รหัสผ่าน ชื่อ นามสกุล เบอร์โทร → แนบข้อมูลอื่นมาด้วย เช่น บทบาท → ข้อมูลไม่ถูกต้อง และบอกว่า "ไม่อนุญาตให้ส่งฟิลด์นี้"
- อีเมลถูกตัดช่องว่างและเก็บเป็นตัวพิมพ์เล็ก → สมัคร A@B.com หลังจากมี a@b.com อยู่แล้ว → ข้อมูลไม่ถูกต้อง "อีเมลนี้ถูกใช้งานแล้ว"
- อีเมลต้องอยู่ในรูปแบบชื่อ@โดเมน.นามสกุลอย่างน้อย 2 ตัวอักษร → ผิดรูปแบบ → ข้อมูลไม่ถูกต้อง
- อีเมลซ้ำกับบัญชีใดก็ได้ รวมบัญชีที่ถูกระงับหรือถูกลบไปแล้ว → ข้อมูลไม่ถูกต้อง
- สมัครด้วยอีเมลเดียวกันสองครั้งพร้อมกัน → สำเร็จหนึ่งครั้ง อีกครั้งถูกปฏิเสธว่าข้อมูลมีอยู่แล้ว
- กรอกผิดหลายช่อง → บอกครบทุกช่องในครั้งเดียว ช่องละหนึ่งข้อความ
- รหัสผ่านต้องยาว 8 ถึง 72 ไบต์ และมีทั้งตัวอักษรและตัวเลข → ไม่ผ่าน → ข้อมูลไม่ถูกต้อง (ยาว 73 ถูกปฏิเสธ ไม่ถูกตัดทิ้งเงียบ ๆ)
- เบอร์โทรบังคับ ใช้ได้แค่ตัวเลข ขีด ช่องว่าง วงเล็บ และเครื่องหมายบวก ยาว 8 ถึง 20 ตัว → ไม่ผ่าน → ข้อมูลไม่ถูกต้อง
- ชื่อและนามสกุลห้ามว่าง และยาวไม่เกิน 100 ตัวอักษร
- ข้อมูลที่ส่งมาอ่านไม่ออก → คำขอผิดรูปแบบ
- เทสที่มี: ยังไม่มีเทส

AC-2: เข้าสู่ระบบด้วยช่องทางเดียวกันทุกบทบาท
- อีเมลและรหัสถูก และบัญชียังใช้งานได้ → สำเร็จ บันทึกเวลาเข้าสู่ระบบล่าสุด และมีบันทึกในประวัติการใช้งาน
- อีเมลไม่มีในระบบ, รหัสผิด, บัญชีที่สมัครผ่าน Google/Facebook ที่ยังไม่ตั้งรหัส, บัญชีผู้ดูแลที่ถูกลบ → ได้ข้อความ "อีเมลหรือรหัสผ่านไม่ถูกต้อง" เหมือนกันทุกกรณี
- กรณีไม่พบอีเมลหรือบัญชีไม่มีรหัส ระบบเสียเวลาตรวจรหัสเท่ากับกรณีปกติ → จับเวลากรณีอีเมลไม่มีเทียบกับรหัสผิดอย่างละ 50 ครั้ง ค่ากลางต้องต่างกันไม่เกิน 20%
- บัญชีถูกระงับแต่รหัสถูก → "บัญชีนี้ถูกระงับการใช้งาน กรุณาติดต่อผู้ดูแลระบบ" · รหัสผิด → ข้อความรหัสผิดตามปกติ (ตรวจสถานะบัญชีหลังตรวจรหัสเท่านั้น)
  - [ยอมรับความเสี่ยง] คนที่รู้รหัสผ่านอยู่แล้วจะรู้ว่าบัญชีนั้นถูกระงับ
- ไม่กรอกอะไรเลย → ได้ข้อความรหัสผิด (ไม่ตรวจรูปแบบ) และนับเป็นการล็อกอินผิดหนึ่งครั้ง
- จำกัดความถี่ นับที่ฐานข้อมูลในช่วง 15 นาทีย้อนหลัง
  - ผิด 5 ครั้งจากคู่อีเมลกับ IP เดียวกัน → ครั้งถัดไปจากคู่นั้นถูกจำกัด ได้ข้อความ "เข้าสู่ระบบผิดหลายครั้งเกินไป กรุณาลองใหม่ใน N นาที" พร้อมบอกจำนวนวินาทีที่ต้องรอ
  - ผิด 20 ครั้งจาก IP เดียวกันไม่ว่าอีเมลไหน → ครั้งถัดไปจาก IP นั้นถูกจำกัด
  - ติดทั้งสองแบบ → ต้องรอตามแบบที่นานกว่า
  - นับเฉพาะกรณีรหัสผิดหรืออีเมลไม่มี กรณีบัญชีถูกระงับไม่นับ
  - ถูกจำกัดแล้ว → ถูกจำกัดแม้รหัสที่ส่งมาจะถูก และได้ผลเหมือนกันไม่ว่าอีเมลนั้นจะมีบัญชีหรือไม่
  - อีเมลเดียวกันจาก IP อื่น → ไม่ถูกจำกัด คนอื่นจึงล็อกบัญชีเหยื่อจากเครื่องตัวเองไม่ได้
  - เข้าสู่ระบบสำเร็จ → ล้างความผิดของคู่อีเมลกับ IP นั้น แต่ไม่ล้างตัวนับของ IP ที่มาจากอีเมลอื่น
  - ความผิดที่เก่ากว่า 15 นาที → ไม่นับ และถูกลบตอนบันทึกความผิดครั้งใหม่
  - IP ใช้กติกาเดียวกับประวัติการใช้งาน (ดู AC-13) ผู้ใช้จึงปลอม IP เพื่อหลบไม่ได้
  - [ยังไม่ยืนยัน] ยิงพร้อมกันจำนวนมากอาจเกินเพดานได้เล็กน้อย เพราะการนับกับการบันทึกไม่ได้ล็อกด้วยกัน
- เทสที่มี: account/ratelimit_test.go (7 เทส), account/oauth_test.go ข้อล็อกอินด้วยรหัสของบัญชี OAuth · กรณีจับเวลายังไม่มีเทส

AC-3: อายุและการหมุนเวียนของการล็อกอิน
- ล็อกอินแล้วได้ access token อายุ 30 นาที และ refresh token อายุ 30 วัน (ปรับได้ใน env)
- access token หมดอายุ, ถูกปลอม, ลงนามด้วยวิธีอื่น, ออกโดยระบบอื่น หรือระบุบทบาทที่ไม่รู้จัก → ถูกปฏิเสธว่ายังไม่ได้เข้าสู่ระบบ
- ฐานข้อมูลเก็บแค่ค่า hash ของ refresh token ไม่เก็บตัวจริง
- ต่ออายุด้วย refresh token ที่ยังใช้ได้ → ได้ token คู่ใหม่ และใบเดิมถูกยกเลิกทันทีในคำสั่งเดียว
- ต่ออายุด้วยใบที่ใช้ไปแล้ว หมดอายุ ออกจากระบบไปแล้ว มั่ว หรือว่าง → ถูกปฏิเสธ
- ต่ออายุของบัญชีที่ถูกระงับ → ถูกปฏิเสธ และใบนั้นถูกใช้ไปแล้วด้วย
- token ใบใหม่ใช้บทบาท ชื่อ และสาขาจากฐานข้อมูล ณ ตอนต่ออายุ
- เปลี่ยนรหัสผ่านสำเร็จ → refresh token ทุกใบของบัญชีนั้นใช้ไม่ได้ทันที รวมใบของเครื่องที่กำลังใช้อยู่
  - [ยอมรับความเสี่ยง] access token ใบเดิมยังใช้ได้จนหมดอายุ สูงสุด 30 นาที
- ออกจากระบบด้วย refresh token ค่าใดก็ได้ → สำเร็จเหมือนกันหมด · ไม่ส่งข้อมูลมาเลย → คำขอผิดรูปแบบ
- ทุกคำขอที่ต้องล็อกอิน ระบบอ่านบัญชีจากฐานข้อมูล → บัญชีถูกลบหรือถูกระงับ → ถูกปฏิเสธทันทีแม้ token ยังไม่หมดอายุ
- admin ที่ไม่มีสาขาผูกอยู่ → ถูกปฏิเสธ

AC-4: Admin ถูกล็อกไว้ที่สาขาเดียว (กฎเหล็ก)
- สาขาของ admin อ่านจากฐานข้อมูลทุกคำขอ ไม่ได้อ่านจาก token
- หน้ารายการของ admin ที่ขอดูสาขาอื่น → ไม่มีสิทธิ์
- admin ไม่ระบุสาขา → ระบบใช้สาขาของตัวเอง ไม่ใช่ทุกสาขา เช่น รายการจองทุกใบเป็นของสาขาตัวเอง
- admin ระบุสาขาของตัวเอง → ใช้ได้ตามปกติ
- super admin ไม่ระบุสาขาในหน้ารายการ → เห็นทุกสาขา · ในการแก้ข้อมูลสาขาหรือเพิ่มห้อง → ถูกปฏิเสธ "กรุณาระบุสาขา (branch_id)"
- admin สาขา A แตะข้อมูลรายชิ้นของสาขา B → ผลไม่เหมือนกันทุกจุด
  - อนุมัติหรือปฏิเสธการจอง → ไม่พบข้อมูล
  - ลบรูปสาขาโดยใช้รหัสรูปของสาขา B → ไม่พบข้อมูล
  - ดูใบจอง ยกเลิกใบจอง ตั้งนัดทำสัญญา แก้ เปลี่ยนสถานะ ลบห้อง อัปโหลดรูปห้อง ลบรูปห้อง → ไม่มีสิทธิ์
  - [ช่องว่าง] คอมเมนต์ในโค้ดตั้งใจให้ข้อมูลรายชิ้นตอบไม่พบข้อมูลเพื่อไม่ยืนยันว่ารหัสมีจริง แต่มีแค่การอนุมัติกับปฏิเสธที่ทำตาม
- super admin ย้าย admin จากสาขา A ไป B → admin คนนั้นใช้ token เดิมต่อได้ และเห็นสาขา B ทันที ขอดูสาขา A → ไม่มีสิทธิ์
- รายชื่อสมาชิกแสดงสมาชิกทั้งระบบ เพราะสมาชิกไม่ผูกกับสาขา ส่วนประวัติการจองของสมาชิกรายคนที่ admin เห็น มีเฉพาะใบในสาขาตัวเอง (ดู AC-28)
- เทสที่มี: shared/access/access_test.go, booking/statemachine_test.go ข้อข้ามสาขา, account/revocation_test.go ข้อย้ายสาขา, storage/asset_test.go ข้ออัปรูปห้องข้ามสาขา, room/images_test.go ข้อลบรูปข้ามสาขา

AC-5: Member เห็นเฉพาะของตัวเอง
- member A เปิดใบจองของ member B → ไม่พบข้อมูล (ไม่ตอบว่าไม่มีสิทธิ์ เพื่อไม่ยืนยันว่ารหัสนั้นมีจริง)
- member A แจ้งชำระเงินหรือยกเลิกใบของ member B → ไม่พบข้อมูล
- member เข้าส่วนของ admin หรือ super admin → ไม่มีสิทธิ์
- admin หรือ super admin สร้างการจอง ดูรายการจองของตัวเอง หรือแจ้งชำระเงิน → ไม่มีสิทธิ์ (ทำได้เฉพาะ member)
- ดูแจ้งเตือน → ได้ไม่เกิน 30 รายการล่าสุด พร้อมจำนวนที่ยังไม่อ่านทั้งหมด (นับเกิน 30 ได้)
- แจ้งเตือนแต่ละรายการมีหัวข้อ ข้อความ ลิงก์ไปหน้าใบจอง และเวลาที่อ่าน (ถ้าอ่านแล้ว)
- กดอ่านทั้งหมด → ทุกรายการที่ยังไม่อ่านของผู้ใช้นั้นเป็นอ่านแล้ว
- กดอ่านรายการเดียว → อ่านรายการนั้น · ถ้าเป็นของคนอื่นหรือไม่มีจริง → สำเร็จเหมือนกันโดยไม่เปลี่ยนอะไร
- กดอ่านโดยไม่ส่งข้อมูลมา หรือรหัสแจ้งเตือนผิดรูปแบบ → คำขอผิดรูปแบบ
- [ช่องว่าง] รหัสแจ้งเตือนที่ระบบส่งออกขึ้นต้นด้วย usr แต่ตอนกดอ่านรับเฉพาะรหัสที่ขึ้นต้นด้วย ntf → เอารหัสที่ได้ไปกดอ่านตรง ๆ ไม่ได้
- เทสที่มี: httpx/errorenvelope_test.go ข้อ member เข้าส่วน admin · ที่เหลือยังไม่มีเทส

AC-6: จองรายวันคิดเงินตามจำนวนคืน
- จำนวนคืน = วันเช็คเอาท์ ลบ วันเข้าพัก เช่น 5 ถึง 8 มี.ค. = 3 คืน
- จอง 3 คืนในห้องราคา 1,200 ต่อคืน → สำเร็จ ยอด 3,600 สถานะรอชำระเงิน และได้รหัสจองรูปแบบ PT-001
- ยอดถูกบันทึกครั้งเดียวตอนจอง → แก้ราคาห้องเป็น 2,000 ทีหลัง → ใบเดิมยังเป็น 3,600
- วันเช็คเอาท์ไม่อยู่หลังวันเข้าพัก → ข้อมูลไม่ถูกต้อง (ฐานข้อมูลกันซ้ำอีกชั้น)
- วันเข้าพักเป็นวันที่ผ่านมาแล้วตามปฏิทินไทย → ข้อมูลไม่ถูกต้อง · เป็นวันนี้ → จองได้ (ดู AC-22)
- วันที่ต้องอยู่ในรูปแบบปี-เดือน-วัน → ผิดรูปแบบหรือไม่ส่งมา → ข้อมูลไม่ถูกต้อง
- ประเภทการเข้าพักไม่ใช่รายวันหรือรายเดือน → ข้อมูลไม่ถูกต้อง · ไม่ตรงกับประเภทที่ห้องเปิดรับ → "ห้องนี้ไม่ได้เปิดให้จองแบบที่เลือก"
- ไม่เลือกห้อง → ข้อมูลไม่ถูกต้อง · รหัสห้องผิดรูปแบบ → คำขอผิดรูปแบบ · ห้องไม่มีจริงหรือถูกลบ → ไม่พบข้อมูล
- ช่องบังคับคือชื่อ นามสกุล และเบอร์ของผู้เข้าพัก (กติกาเบอร์เดียวกับ AC-1) · เบอร์ฉุกเฉินไม่บังคับแต่ถ้ากรอกต้องถูกรูปแบบ · ความสัมพันธ์ของผู้ติดต่อฉุกเฉินไม่ตรวจ
- ไม่จำกัดความยาวชื่อผู้เข้าพัก ไม่จำกัดจำนวนคืน และไม่มีช่องจำนวนผู้เข้าพัก
- จองสำเร็จ → member ได้แจ้งเตือน "สร้างรายการจองสำเร็จ" ที่มีรหัสจอง และมีบันทึกในประวัติการใช้งานของสาขาที่ห้องอยู่
- เทสที่มี: ยังไม่มีเทสเฉพาะ (เทสของ AC-10 ใช้การจองเป็นขั้นเตรียมข้อมูลเท่านั้น)

AC-7: จองรายเดือนเก็บแค่ค่าทำสัญญา
- ห้อง 5,000 ต่อเดือน ในสาขาที่ตั้งค่าทำสัญญา 500 → ยอดของใบจองคือ 500 ค่าเช่าไม่ถูกบันทึกในใบจอง และไม่มีจำนวนคืน
- ค่าทำสัญญาถูกคัดลอกลงใบตอนจอง → สาขาแก้เป็น 800 ทีหลัง → ใบเดิมยังเป็น 500
- วันที่ต้องการเข้าอยู่บังคับ → ไม่ส่งหรือเป็นวันที่ผ่านมาแล้ว → ข้อมูลไม่ถูกต้อง (ฐานข้อมูลกันซ้ำอีกชั้น)
- วันที่ต้องการทำสัญญาไม่บังคับ และไม่ตรวจว่าต้องเป็นอนาคตหรือสัมพันธ์กับวันเข้าอยู่ → ถ้ากรอกผิดรูปแบบ → ข้อมูลไม่ถูกต้อง
- จองรายเดือนในห้องที่เปิดแบบรายวัน → ข้อมูลไม่ถูกต้อง
- เทสที่มี: ยังไม่มีเทส

AC-8: ห้องเดียวจองซ้อนไม่ได้ (กฎเหล็ก)
- ใบจองที่ถือห้องไว้คือ รอชำระเงิน, รอตรวจสอบ, อนุมัติแล้ว · ใบที่ยกเลิกไม่ถือห้อง · ในฐานข้อมูลมีสถานะการจองแค่ 4 ค่านี้ (ไม่มีสถานะถูกปฏิเสธและเข้าพักครบแล้ว)
- ห้องที่มีใบรายเดือนถืออยู่ → จองใหม่ทุกแบบในห้องนั้นไม่ได้เลยไม่ว่าวันไหน → "ขออภัย ห้องนี้ถูกจองไปแล้วในช่วงวันที่ที่เลือก กรุณาเลือกห้องหรือวันที่อื่น"
- ใบรายวันสองใบถือว่าทับกันเมื่อวันเข้าพักใหม่อยู่ก่อนวันเช็คเอาท์เดิม และวันเช็คเอาท์ใหม่อยู่หลังวันเข้าพักเดิม → จองทับ → ห้องไม่ว่าง
- จองรายวันที่วันเข้าพักตรงกับวันเช็คเอาท์ของใบเดิมพอดี → จองได้
- ห้องสถานะมีผู้เช่าหรือปิดปรับปรุง → ห้องไม่ว่าง
- สองคนจองห้องเดียวกันพร้อมกัน → สำเร็จคนเดียว เพราะระบบล็อกแถวห้องไว้ตลอดการจอง
- [ช่องว่าง] กฎห้ามทับและกฎใบรายเดือนได้ทีละใบบังคับที่ตัวโปรแกรมเท่านั้น ฐานข้อมูลไม่มี constraint รองรับ ขัด AGENTS.md ข้อ 4 → ใส่ข้อมูลตรงเข้าฐานข้อมูลแล้วสร้างใบซ้อนได้
- [ช่องว่าง] ห้องในสาขาที่ปิดใช้งาน → ยังจองได้ตามปกติ ทั้งที่หน้าสาธารณะซ่อนห้องนั้นแล้ว (ดู AC-12, AC-27)
- [ช่องว่าง] ใบรายวันที่ค้างอยู่ไม่กันการจองรายเดือน → ถ้าแอดมินเปลี่ยนห้องจากรายวันเป็นรายเดือนระหว่างมีใบรายวันค้าง ห้องจะรับใบรายเดือนซ้อนได้ (ดู AC-19)
- รหัสจองรันเลขต่อเนื่อง อย่างน้อย 3 หลัก → เกิน 999 แล้วยาวขึ้นเอง เช่น PT-1000
- การอ้างถึงใบจองในระบบใช้รหัสภายในที่ขึ้นต้นด้วย bkg ไม่ใช่รหัส PT → ใช้รหัส PT อ้างถึง → คำขอผิดรูปแบบ
- เทสที่มี: booking/statemachine_test.go ข้อห้องยังถูกล็อกหลังถูกปฏิเสธ และข้อสถานะมีแค่ 4 ค่า · การจองพร้อมกันยังไม่มีเทส

AC-9: แจ้งชำระเงินพร้อมสลิป
- member แจ้งชำระใบรอชำระเงินของตัวเอง พร้อมแนบสลิป ยอดโอน เวลาโอน และหมายเหตุ → สำเร็จ ใบเปลี่ยนเป็นรอตรวจสอบ และได้ข้อมูลการแจ้งชำระล่าสุดกลับมาเลย
- ลำดับการตรวจ ผิดข้อแรกที่เจอแล้วหยุดทันที
  - รหัสใบจองผิดรูปแบบ → คำขอผิดรูปแบบ
  - ข้อมูลทั้งก้อนใหญ่เกินเพดานไฟล์ (ค่าเริ่มต้น 5MB) บวก 1MB หรืออ่านฟอร์มไม่ได้ → คำขอผิดรูปแบบ
  - ยอดโอนไม่ใช่ตัวเลขหรือว่าง → ข้อมูลไม่ถูกต้อง
  - เวลาโอนอ่านไม่ออกหรือว่าง → ข้อมูลไม่ถูกต้อง
  - หมายเหตุไม่ใช่ข้อความ UTF-8 → คำขอผิดรูปแบบ
  - ไม่แนบสลิป, สลิปไม่ใช่รูป JPG PNG WEBP ตามเนื้อไฟล์จริง, หรือใหญ่เกินเพดาน → คำขอผิดรูปแบบ
  - ใบจองไม่มีจริงหรือเป็นของคนอื่น → ไม่พบข้อมูล
  - ใบไม่ได้อยู่สถานะรอชำระเงิน → "รายการจองนี้ไม่อยู่ในสถานะที่แจ้งชำระเงินได้"
  - ยอดโอนไม่มากกว่า 0 หรือเวลาโอนอยู่ในอนาคตเกิน 5 นาที → ข้อมูลไม่ถูกต้อง
- [ช่องว่าง] สลิปถูกเขียนลงดิสก์ก่อนตรวจใบจอง ยอด และเวลา → คำขอที่ตกขั้นหลังทิ้งไฟล์กำพร้าไว้
- ไม่เทียบยอดโอนกับยอดที่ต้องจ่าย → ยอดไม่ตรงก็รับตามปกติ แอดมินต้องเทียบเอง
- เวลาโอนไม่มีขอบเขตย้อนหลัง (วันโอนเมื่อ 2 ปีก่อนก็ผ่าน) · เวลาที่ไม่ระบุเขตเวลาถือเป็นเวลาไทย (ดู AC-22)
- การแจ้งชำระแต่ละครั้งเป็นหนึ่งรายการแยกกัน → แจ้งใหม่หลังถูกปฏิเสธจะเพิ่มรายการใหม่ ไม่เขียนทับของเดิม
- สลิปเก็บในโฟลเดอร์แยกตามปีและเดือน ตั้งชื่อไฟล์ใหม่แบบสุ่ม ไม่ใช้ชื่อไฟล์ของผู้ใช้
- สำเร็จ → member ได้แจ้งเตือน "ส่งหลักฐานการชำระเงินแล้ว" และมีบันทึกในประวัติการใช้งานพร้อมรหัสจองและยอดโอน
- [ยังไม่ยืนยัน] แจ้งชำระใบเดียวกันสองครั้งพร้อมกัน → น่าจะสำเร็จทั้งคู่และได้สองรายการ เพราะการตรวจสถานะไม่ได้ล็อก
- เทสที่มี: ยังไม่มีเทสเฉพาะ (เทสของ AC-10 ใช้เป็นขั้นเตรียมข้อมูล)

AC-10: อนุมัติหรือปฏิเสธการจอง
- ลำดับการตรวจ: รหัสผิดรูปแบบ → ใบไม่มีจริง → ข้ามสาขา → ไม่ได้อยู่สถานะรอตรวจสอบ → ปฏิเสธโดยไม่ใส่เหตุผล
- อนุมัติใบรอตรวจสอบ → ใบเป็นอนุมัติแล้ว บันทึกผู้ตรวจและเวลาที่ตรวจ · การแจ้งชำระทุกรายการของใบที่ยังรอตรวจเป็นอนุมัติพร้อมผู้ตรวจและเวลา
- อนุมัติใบรายเดือน → ห้องเป็นมีผู้เช่าในธุรกรรมเดียวกัน · อนุมัติใบรายวัน → สถานะห้องไม่เปลี่ยน
- ปฏิเสธใบรอตรวจสอบพร้อมเหตุผล → ใบกลับไปเป็นรอชำระเงิน และห้องยังถูกถือไว้ (ดู AC-8) · การแจ้งชำระครั้งนั้นเป็นถูกปฏิเสธและเก็บเหตุผลไว้ที่การแจ้งชำระ ไม่ใช่ที่ใบจอง
- ปฏิเสธโดยไม่ใส่เหตุผล หรือเหตุผลมีแต่ช่องว่าง → "กรุณาระบุเหตุผลที่ปฏิเสธ เพื่อแจ้งกลับไปยังสมาชิก"
- อนุมัติไม่ต้องส่งข้อมูลอะไรมา
- อนุมัติหรือปฏิเสธใบที่ไม่ได้อยู่สถานะรอตรวจสอบ → "รายการจองนี้ไม่ได้อยู่ในสถานะรอตรวจสอบ"
- admin สาขา A อนุมัติหรือปฏิเสธใบของสาขา B → ไม่พบข้อมูล
- สำเร็จ → member ได้แจ้งเตือนที่มีรหัสจอง (กรณีปฏิเสธมีเหตุผลในข้อความ) และมีบันทึกในประวัติการใช้งาน
- มีเทสว่ากดอนุมัติพร้อมกันสองครั้งแล้วสำเร็จครั้งเดียว [ยังไม่ยืนยัน] แต่ในโค้ดคำสั่งเปลี่ยนสถานะไม่ได้เช็คสถานะเดิม และการตรวจสถานะเกิดก่อนเริ่มธุรกรรม → ผลอาจขึ้นกับจังหวะ ต้องรันซ้ำหลายรอบเพื่อยืนยัน
- ในรายการจองของแอดมิน ใบที่กลับเป็นรอชำระเงินหลังถูกปฏิเสธไม่มีข้อมูลการแจ้งชำระแนบมา → ต้องเปิดดูใบนั้นรายใบถึงจะเห็นเหตุผล
- เทสที่มี: booking/statemachine_test.go (อนุมัติ, ปฏิเสธ, สถานะผิด, ข้ามสาขา, แจ้งเตือน, อนุมัติพร้อมกัน)

AC-11: ยกเลิกแล้วห้องต้องกลับมาขายได้ (กฎเหล็ก)
- member ยกเลิกใบรอชำระเงินของตัวเอง → ใบเป็นยกเลิก และบันทึกเวลาที่ยกเลิก
- member ยกเลิกใบสถานะอื่น → "รายการจองนี้ไม่สามารถยกเลิกเองได้ กรุณาติดต่อผู้ดูแลระบบของสาขา"
- admin ในสาขาตัวเองหรือ super admin ยกเลิกใบสถานะใดก็ได้
- [ช่องว่าง] admin ยกเลิกใบที่ยกเลิกไปแล้ว → สำเร็จอีกครั้ง เวลายกเลิกถูกเขียนทับ member ได้แจ้งเตือนซ้ำ และมีบันทึกซ้ำ
- [ช่องว่าง] คำสั่งยกเลิกในฐานข้อมูลไม่ได้ผูกเงื่อนไขสาขา ตรวจสาขาในตัวโปรแกรมอย่างเดียว ขัดกับที่ README อ้างว่าคำสั่งแก้ข้อมูลของแอดมินผูกสาขาเสมอ
- ยกเลิกใบรายเดือน → ห้องที่มีผู้เช่ากลับเป็นว่างในธุรกรรมเดียวกัน เฉพาะเมื่อไม่มีใบรายเดือนอื่นถือห้องอยู่ · ห้องที่ปิดปรับปรุงหรือว่างอยู่แล้วไม่ถูกแตะ
- ยกเลิกใบรายวัน → สถานะห้องไม่เปลี่ยน (ใบรายวันไม่เคยเปลี่ยนสถานะห้อง)
- ห้องที่ถูกปล่อยแล้ว → จองใหม่ได้ทันที
- สำเร็จ → เจ้าของใบได้แจ้งเตือน "รายการจองถูกยกเลิก" และมีบันทึกในประวัติการใช้งาน
- เทสที่มี: ยังไม่มีเทส

AC-12: ค้นหาห้องว่าง
- ผลค้นหามีเฉพาะห้องที่ยังไม่ถูกลบ สถานะว่าง และสาขาของห้องเปิดใช้งาน
- ระบุวันเข้าพักและวันเช็คเอาท์ → ไม่มีห้องที่มีใบรายวันทับช่วงนั้น (สูตรเดียวกับ AC-8) · ห้องที่ใบเดิมเช็คเอาท์ตรงวันเข้าพักที่ค้นหา → อยู่ในผล · ระบุวันเดียว → ไม่กรองใบรายวัน
- ห้องที่มีใบรายเดือนถืออยู่ → ถูกตัดออกเฉพาะเมื่อวันเข้าอยู่ของใบนั้นไม่เกินวันเข้าอยู่ที่ค้นหา (ไม่ระบุใช้วันนี้ตามนาฬิกาของฐานข้อมูล)
- [ช่องว่าง] กติกาข้อบนหลวมกว่าตอนจองจริง → ห้องที่มีคนจองรายเดือนเข้าอยู่ในอนาคตโผล่ในผลค้นหา แต่กดจองแล้วห้องไม่ว่าง (ดู AC-8)
- ค้นแบบรายวันที่วันเช็คเอาท์ไม่อยู่หลังวันเข้าพัก → ข้อมูลไม่ถูกต้อง · ไม่ระบุประเภท → ไม่ตรวจลำดับวันที่
- ตัวกรองที่รับ: สาขา ประเภทห้อง ประเภทการเข้าพัก วันเข้าพัก วันเช็คเอาท์ วันเข้าอยู่ ราคาต่ำสุด ราคาสูงสุด หน้า ขนาดหน้า
- ไม่ระบุหน้า → หน้า 1 หน้าละ 20 พร้อมจำนวนทั้งหมดและจำนวนหน้า · ขอหน้าละ 500 → ได้ไม่เกิน 100
- หน้าหรือขนาดหน้าเป็น 0 ติดลบ หรือไม่ใช่ตัวเลข, ประเภทไม่รู้จัก, วันที่ผิดรูปแบบ, ราคาไม่ใช่ตัวเลข, รหัสสาขาหรือประเภทห้องผิดรูปแบบ → คำขอผิดรูปแบบ
- เรียงตามสาขาแล้วตามเลขห้อง · แต่ละห้องมีสิ่งอำนวยความสะดวกของห้องนั้นเอง แต่ไม่มีแกลเลอรีรูป
- เทสที่มี: room/amenities_test.go ข้อค้นหาได้ amenity รายห้อง, room/closed_test.go ข้อสาขาที่ปิด, room/images_test.go ข้อค้นหาไม่มีแกลเลอรี

AC-13: บันทึกทุกการกระทำที่เปลี่ยนข้อมูล
- การกระทำที่ถูกบันทึก 29 อย่าง
  - บัญชี: สมัคร, เข้าสู่ระบบ, เข้าสู่ระบบผ่าน Google/Facebook, ผูกบัญชีภายนอก, สมัครผ่าน Google/Facebook, แก้โปรไฟล์, เปลี่ยนรหัสผ่าน
  - ผู้ดูแล: เพิ่ม, แก้, ลบบัญชีผู้ดูแล
  - การจอง: สร้าง, แจ้งชำระ, ยกเลิก, อนุมัติ, ปฏิเสธ, ตั้งนัดทำสัญญา
  - สาขา: แก้รายละเอียด, ตั้งสิ่งอำนวยความสะดวก, แก้สถานที่ใกล้เคียง, เปลี่ยนรูปปก, เพิ่มรูป, ลบรูป
  - ห้อง: สร้าง, แก้, เปลี่ยนรูปปก, เพิ่มรูปแกลเลอรี, ลบรูปแกลเลอรี, เปลี่ยนสถานะ, ลบ
- ทำการกระทำในลิสต์สำเร็จ → มีบันทึกใหม่ที่มีผู้กระทำ บทบาท ชื่อ สาขา การกระทำ ชนิดและรหัสของสิ่งที่ถูกกระทำ รายละเอียดเพิ่มเติม IP และเวลา
- IP ของผู้กระทำ
  - ไม่ได้ตั้ง proxy ที่เชื่อถือ → ใช้ IP ของการเชื่อมต่อจริง ผู้ใช้ส่ง header ปลอม IP มาก็ไม่มีผล
  - คำขอมาจาก proxy ที่ตั้งไว้ว่าเชื่อถือ → ใช้ IP ขวาสุดในรายการที่ไม่ใช่ proxy ค่าปลอมที่ผู้ใช้แอบใส่ไว้ด้านซ้ายไม่มีผล
  - ตั้งค่า proxy ที่เชื่อถือผิดรูปแบบ → ระบบไม่ยอมเริ่มทำงาน
  - รันผ่าน docker โดยไม่มี proxy → IP ที่เห็นอาจเป็นของ docker ไม่ใช่ของผู้ใช้จริง
- ชื่อผู้กระทำมาจากฐานข้อมูล ณ ตอนทำรายการ → แก้ชื่อแล้วบันทึกถัดไปใช้ชื่อใหม่ทันที
- สาขาของบันทึก
  - เรื่องการจอง ห้อง สาขา → สาขาของสิ่งที่ถูกกระทำ
  - เรื่องบัญชีและผู้ดูแล → สาขาของผู้กระทำ (member และ super admin ไม่มีสาขา) → เช่น super admin เพิ่ม admin ให้สาขา A บันทึกนั้นไม่มีสาขา และสาขาไปอยู่ในรายละเอียดเพิ่มเติมแทน
- ต่ออายุ token, ออกจากระบบ, แลกรหัสจาก Google/Facebook, อ่านแจ้งเตือน และล็อกอินผิด → ไม่ถูกบันทึก
- บันทึกไม่สำเร็จ → ข้อผิดพลาดถูกเก็บเงียบ และธุรกรรมหลักไม่ล้มตาม
- ดูประวัติการใช้งาน → admin เห็นเฉพาะบันทึกของสาขาตัวเอง (บันทึกที่ไม่มีสาขาจึงไม่เห็น) · super admin ไม่ระบุสาขา → เห็นทุกบันทึกรวมที่ไม่มีสาขา
- กรองได้ด้วยการกระทำ (ตรงตัว), คำค้นในชื่อผู้กระทำ ชื่อสาขา หรือรหัสสิ่งที่ถูกกระทำ, ผู้กระทำ, บทบาท (บทบาทที่ไม่รู้จัก → คำขอผิดรูปแบบ), สาขา · หน้าละ 20 เรียงใหม่สุดก่อน และมีชื่อสาขามาด้วย
- เทสที่มี: middleware/clientip_test.go, config/config_test.go (proxy ที่เชื่อถือ 3 เทส), account/oauth_test.go ข้อบันทึกการล็อกอินผ่าน OAuth

AC-14: รูปภาพสาขาและห้อง อัปโหลดไฟล์หรือใส่ลิงก์ภายนอก
- อัปโหลดไฟล์ได้ 4 แบบ: รูปปกสาขา, รูปแกลเลอรีสาขา (พร้อมคำบรรยายและลำดับ), รูปปกห้อง, รูปแกลเลอรีห้อง (พร้อมลำดับ)
- ไฟล์ที่อัปโหลดเก็บในฐานข้อมูล แล้วระบบบันทึกเป็นลิงก์สาธารณะของไฟล์นั้น (รูปเดโมจาก seed ต่างออกไป ดูหัวข้อข้อมูลตั้งต้น)
- อัปโหลดไฟล์เนื้อเดียวกันซ้ำ → ใช้ไฟล์เดิม ไม่เก็บซ้ำ
- ชนิดไฟล์ตรวจจากเนื้อไฟล์จริง ต้องเป็น JPG PNG หรือ WEBP → ไม่ใช่ → คำขอผิดรูปแบบ · ใหญ่เกินเพดาน → คำขอผิดรูปแบบ · ไม่แนบไฟล์ → "กรุณาแนบไฟล์ในช่อง image"
- ลำดับรูปไม่ใช่จำนวนเต็ม → คำขอผิดรูปแบบ · ไม่ระบุ → 0 · คำบรรยายไม่ใช่ UTF-8 หรือยาวเกิน 200 ตัวอักษร → ข้อมูลไม่ถูกต้อง
- [ช่องว่าง] ไฟล์ถูกเก็บก่อนตรวจสิทธิ์สาขาและก่อนตรวจลำดับรูป → คำขอที่ถูกปฏิเสธทิ้งไฟล์กำพร้าไว้ในฐานข้อมูล
- ไฟล์รูปเปิดดูได้โดยไม่ต้องล็อกอิน · เบราว์เซอร์เก็บ cache ได้ถาวรเพราะเนื้อไฟล์ของลิงก์หนึ่งไม่มีวันเปลี่ยน · ขอซ้ำพร้อมบอกว่ามีไฟล์เดิมแล้ว → ไม่ส่งไฟล์ซ้ำ · ไม่มีไฟล์นั้น → ไม่พบข้อมูล
- ใส่ลิงก์รูปภายนอกเข้าแกลเลอรีสาขาหรือห้องได้ → ลิงก์ต้องเป็น http หรือ https ที่มีโดเมน ยาวไม่เกิน 2048 ตัว → ลิงก์ javascript, data, path ลอย ๆ หรือค่าว่าง → ข้อมูลไม่ถูกต้อง
- ช่องรูปปกตอนเพิ่มหรือแก้ห้อง และตอนแก้รายละเอียดสาขา ใช้กติกาเดียวกัน แต่ปล่อยว่างได้
- แกลเลอรีห้องเป็นคนละส่วนกับรูปปก → เพิ่มหรือลบรูปแกลเลอรีไม่แตะรูปปก · รูปแกลเลอรีห้องเรียงตามลำดับแล้วตามรหัส · รูปแกลเลอรีสาขาเรียงตามลำดับแล้วตามเวลาที่เพิ่ม
- ลบรูปสาขาที่ไม่มีหรือเป็นของสาขาอื่น → ไม่พบข้อมูล
- ลบรูปแกลเลอรีของห้องคนละสาขา → ไม่มีสิทธิ์ · รูปไม่มีจริง → ไม่พบข้อมูล
- [ช่องว่าง] ลบรูปโดยระบุห้องหนึ่งแต่รหัสรูปเป็นของอีกห้องในสาขาเดียวกัน → รูปนั้นถูกลบ และบันทึกผูกกับห้องที่ระบุ ไม่ใช่ห้องเจ้าของรูป
- เทสที่มี: storage/asset_test.go (8 เทส), room/images_test.go (5 เทส)

AC-15: ความปลอดภัยและความทนทานพื้นฐาน
- ทุกคำสั่งฐานข้อมูลใช้ค่าแบบ parameter ไม่มีการต่อข้อความของผู้ใช้เข้าคำสั่ง ตรวจด้วย code review ไม่ใช่เทส
- ข้อผิดพลาดภายในระบบ → ผู้ใช้เห็นแค่ "เกิดข้อผิดพลาดภายในระบบ" ไม่มีรายละเอียดภายในหรือข้อความ SQL รายละเอียดจริงอยู่ใน log ฝั่ง server
- โปรแกรมพังระหว่างทำงาน → server ไม่ล้ม และผู้ใช้ได้ข้อผิดพลาดภายในระบบในรูปแบบเดียวกับข้อผิดพลาดอื่น
- ข้อความที่ผู้ใช้เห็นเป็นภาษาไทยทั้งหมด รวมกรณีเรียกที่อยู่ที่ไม่มี ("ไม่พบข้อมูลที่ต้องการ") และเรียกผิดวิธี ("ไม่รองรับ HTTP method นี้")
- ไม่ได้ตั้งที่อยู่ฐานข้อมูล หรือรหัสลับของ token สั้นกว่า 32 ตัว → ระบบไม่ยอมเริ่มทำงาน
- ทุกคำตอบมีรหัสติดตามคำขอ → ถ้าผู้เรียกส่งมาใช้ค่านั้น ถ้าไม่ส่งระบบสุ่มให้
- อนุญาตให้เว็บเรียกข้ามโดเมนได้เฉพาะโดเมนในรายการที่ตั้งไว้ (ค่าเริ่มต้น localhost:3000 และ localhost:5173)
- ข้อมูลที่ส่งมาใหญ่เกิน 1MB หรือมีข้อมูลซ้อนมากกว่าหนึ่งชุด → คำขอผิดรูปแบบ
- เปิดโฟลเดอร์ไฟล์บนดิสก์เพื่อดูรายชื่อไฟล์ → ไม่พบข้อมูล
- รหัสผ่านเก็บเป็น bcrypt (cost 12) · ฐานข้อมูลบังคับว่าช่องรหัสผ่านต้องเป็น bcrypt หรือว่างเท่านั้น
- ตารางถูกอัปเดตเองตอนเริ่มทำงาน ไฟล์ละหนึ่งธุรกรรม และข้ามไฟล์ที่ทำไปแล้ว
- สั่งปิดระบบ → รอคำขอที่ค้างอยู่ได้สูงสุด 20 วินาที
- server มีเวลาจำกัดในการอ่านและเขียน กันการเชื่อมต่อค้างนาน
- โหมด production → log เป็น JSON ระดับ info · โหมดอื่น → log เป็นข้อความระดับ debug
- container รันด้วยผู้ใช้ที่ไม่ใช่ root และตรวจสุขภาพระบบทุก 30 วินาที
- เทสที่มี: httpx/errorenvelope_test.go ข้อโปรแกรมพังและข้อที่อยู่ที่ไม่มี · ที่เหลือยังไม่มีเทส

AC-16: การจองที่ไม่จ่ายเงินหมดอายุเอง [ยังไม่ implement]

  - ถูกปฏิเสธแล้วกลับเป็นรอชำระเงิน → หมดอายุใน 24 ชั่วโมงนับจากเวลาที่ปฏิเสธ
  - ใบรอชำระเงินที่เลยเวลาหมดอายุ → ระบบเปลี่ยนเป็นยกเลิก และปล่อยห้องตาม AC-11
  - บันทึกการหมดอายุในประวัติการใช้งานโดยไม่มีผู้กระทำ → ต้องเพิ่มบทบาท "ระบบ" ในฐานข้อมูลก่อน
- ห้ามเขียนเทสยืนยันจนกว่าจะทำจริง

AC-17: สลิปโอนเงิน ยังไม่ตรวจสิทธิ์ก่อนให้ดู

- ช่องทางเดียวกันนี้ใช้ให้บริการรูปเดโมของสาขาด้วย → ปิดช่องทางนี้เฉย ๆ จะทำให้รูปเดโมหายไปด้วย
- [ช่องว่าง] ไฟล์ .gitignore ของ backend ไม่ได้กันโฟลเดอร์ uploads แล้ว และ docker เก็บสลิปไว้ในโฟลเดอร์ของ repo → สลิปจริงของลูกค้าอาจถูก commit เข้า git ได้
- [ยังไม่ implement] ดูสลิปผ่านช่องทางที่ตรวจสิทธิ์
  - เจ้าของใบ, admin สาขาเดียวกัน, super admin → เห็นสลิป
  - คนอื่น หรือใบที่ไม่มีจริง → ไม่พบข้อมูลเหมือนกัน
  - ไม่ได้ล็อกอิน → ถูกปฏิเสธว่ายังไม่ได้เข้าสู่ระบบ
- เทสที่มี: ยังไม่มีเทส

AC-18: Super Admin จัดการบัญชีผู้ดูแล
- ดูรายชื่อผู้ดูแล → admin และ super admin ทุกคนที่ยังไม่ถูกลบ รวมคนที่ถูกระงับ เรียง super admin ก่อนแล้วตามวันที่สร้าง พร้อมชื่อสาขา
- เพิ่มผู้ดูแลด้วยอีเมล ชื่อ นามสกุล เบอร์ และสาขา → ได้บัญชีบทบาท admin ที่ถูกปักธงให้ต้องเปลี่ยนรหัสผ่าน
- ข้อมูลที่ตอนเพิ่มส่งไม่ได้หรือระบบตั้งให้เอง
  - ไม่รับรหัสผ่านและไม่รับข้อมูลอื่นนอกจาก 5 ช่อง → ส่งมา → ข้อมูลไม่ถูกต้อง
  - รหัสผ่านตั้งจากค่ารหัสตั้งต้นของผู้ดูแลใน env → ถ้าไม่ตั้งใช้รหัสตั้งต้นของ seed → ถ้าไม่ตั้งทั้งคู่ใช้ Wisetsuk!2026
  - เบอร์ไม่บังคับ แต่ถ้ากรอกต้องถูกรูปแบบ · ชื่อไม่จำกัดความยาว (ต่างจากการสมัครสมาชิก)
- เพิ่มผู้ดูแลผิดเงื่อนไข
  - ไม่เลือกสาขา → "กรุณาเลือกสาขาที่รับผิดชอบ"
  - รหัสสาขาผิดรูปแบบ → คำขอผิดรูปแบบ
  - ไม่มีสาขานั้น → "ไม่พบสาขาที่เลือก"
  - สาขามีผู้ดูแลอยู่แล้ว → "สาขานี้มีผู้ดูแลอยู่แล้ว หนึ่งสาขามีผู้ดูแลได้คนเดียว"
  - อีเมลซ้ำ รวมอีเมลของบัญชีที่ถูกลบไปแล้ว → "อีเมลนี้ถูกใช้งานแล้ว"
- เพิ่มสำเร็จ → มีบันทึกพร้อมอีเมลและสาขา
- แก้ผู้ดูแลเป็นการแทนที่ทั้งชุด → ไม่ส่งชื่อหรือนามสกุล → ข้อมูลไม่ถูกต้อง · ไม่ส่งเบอร์ → เบอร์ถูกล้าง · ไม่ส่งสถานะเปิดใช้งาน → คงค่าเดิม
  - ระบบหาบัญชีเป้าหมายก่อนตรวจข้อมูล → เป้าหมายเป็น member ไม่มีจริง หรือถูกลบแล้ว → ไม่พบข้อมูล
  - เป้าหมายเป็น admin แต่ไม่ระบุสาขา → "ผู้ดูแลระบบต้องมีสาขาที่รับผิดชอบ" · เป้าหมายเป็น super admin แต่ระบุสาขา → "หัวหน้าผู้ดูแลระบบผูกกับสาขาไม่ได้"
  - ย้ายไปสาขาที่มีผู้ดูแลแล้ว → ข้อความสาขามีผู้ดูแลแล้ว
  - [ช่องว่าง] ย้ายไปสาขาที่ไม่มีจริง → เกิดข้อผิดพลาดภายในระบบ (ต่างจากตอนเพิ่มที่ตรวจก่อน)
  - ระงับบัญชีตัวเอง → "ไม่สามารถระงับบัญชีของตนเองได้"
  - ตั้งรหัสผ่านใหม่ให้ → ต้องผ่านกติกา AC-1 · ตั้งรหัสทันที ปักธงให้ต้องเปลี่ยนรหัส และยกเลิก refresh token ทุกใบของบัญชีนั้น เป็นช่องทางเดียวที่ super admin รีเซ็ตรหัสให้คนอื่นได้
  - ระงับบัญชี → token เดิมใช้ไม่ได้ทันที และต่ออายุไม่ได้ (ดู AC-3) แต่ refresh token ไม่ถูกยกเลิก จึงใช้ได้อีกถ้าเปิดบัญชีคืน
  - ย้ายสาขา → ไม่ยกเลิก token แต่ token เดิมเห็นสาขาใหม่ทันที (ดู AC-4)
  - แก้สำเร็จ → มีบันทึกพร้อมสถานะเปิดใช้งานหลังแก้
- ลบผู้ดูแล → เป็นการลบแบบเก็บแถวไว้ (บันทึกเวลาที่ลบและปิดบัญชี) ยกเลิก refresh token ทุกใบ และมีบันทึก
  - ลบตัวเอง → "ไม่สามารถลบบัญชีของตนเองได้" · เป้าหมายไม่ใช่ admin ไม่มีจริง หรือถูกลบไปแล้ว → ไม่พบข้อมูล
  - แถวยังอยู่ → บันทึกประวัติ ผู้ตรวจใบจอง และผู้ตรวจการชำระเงินที่อ้างถึงบัญชีนี้ไม่หลุด
  - บัญชีที่ถูกลบล็อกอินไม่ได้ token เดิมใช้ไม่ได้ และไม่โผล่ในรายชื่อใด ๆ
  - สาขาของคนที่ถูกลบว่างทันที → เพิ่มผู้ดูแลคนใหม่ลงสาขาเดิมได้
- ฐานข้อมูลปฏิเสธการมี admin คนที่สองในสาขาเดียวกันและ super admin คนที่สอง แม้ใส่ข้อมูลตรงโดยไม่ผ่านระบบ
- เทสที่มี: account/staff_test.go (12 เทส)

AC-19: จัดการห้อง
- เพิ่มห้องด้วยข้อมูล สาขา ประเภทห้อง เลขห้อง อาคาร ชั้น ประเภทการเข้าพัก ราคา ค่าน้ำ ค่าไฟ ขนาด คำอธิบาย รูปปก สถานะ และสิ่งอำนวยความสะดวก
  - admin ไม่ระบุสาขา → ใช้สาขาตัวเอง · ระบุสาขาอื่น → ไม่มีสิทธิ์ · super admin ไม่ระบุ → ถูกปฏิเสธให้ระบุสาขา
- แก้ห้องเป็นการแทนที่ทั้งชุด → สาขายึดตามห้องเดิม (สาขาที่ส่งมาถูกเมิน) · ไม่ส่งรูปปก → คงรูปเดิม · ไม่ส่งประเภทห้องหรือขนาด → กลายเป็นว่าง
- กติกาของค่า
  - เลขห้องบังคับและยาวไม่เกิน 20
  - ราคามากกว่า 0, ชั้นมากกว่า 0, ค่าน้ำและค่าไฟไม่ติดลบ
  - ประเภทการเข้าพักเป็นรายวันหรือรายเดือน
  - ไม่ระบุสถานะ → ว่าง · สถานะอื่นนอกจากว่าง มีผู้เช่า ปิดปรับปรุง → ข้อมูลไม่ถูกต้อง
  - ไม่ระบุอาคาร → อาคาร 1
- เลขห้องซ้ำในสาขาเดียวกัน → "เลขห้องนี้มีอยู่ในสาขาแล้ว" รวมถึงเลขของห้องที่ถูกลบไปแล้ว จึงเอาเลขห้องที่ลบแล้วกลับมาใช้ไม่ได้
- สิ่งอำนวยความสะดวกของห้อง: ไม่ส่ง → ไม่แตะของเดิม · ส่งรายการว่าง → ล้างทั้งหมด · รหัสที่ไม่มีจริง → "มีสิ่งอำนวยความสะดวกที่ไม่มีอยู่ในระบบ" และห้องไม่ถูกสร้าง · รหัสซ้ำในรายการ → รับได้
- [ช่องว่าง] ประเภทห้องที่ไม่มีจริง → เกิดข้อผิดพลาดภายในระบบ · ประเภทห้องของอีกสาขา → รับได้ (ไม่ตรวจว่าอยู่สาขาเดียวกัน)
- เปลี่ยนสถานะห้อง → ไม่จำกัดว่าเปลี่ยนจากไหนไปไหน และไม่ตรวจใบจองที่ค้าง · สถานะไม่อยู่ใน 3 ค่า → ข้อมูลไม่ถูกต้อง
- ลบห้อง → เป็นการปิดห้องโดยเก็บแถวไว้ ไม่ตรวจใบจองที่ค้าง · ลบห้องที่ลบแล้วซ้ำ → สำเร็จอีกครั้ง
- [ช่องว่าง] แก้ เปลี่ยนสถานะ ลบ หรืออัปโหลดรูปของห้องที่ถูกลบแล้ว → ยังทำได้ แต่ห้องนั้นไม่โผล่ในรายการห้องของแอดมินแล้ว
- [ช่องว่าง] เปลี่ยนประเภทการเข้าพักหรือสถานะของห้องที่มีใบจองค้าง → ทำได้เลย ไม่มีการตรวจ (ดู AC-8)
- รายการห้องของแอดมิน → ห้องที่ยังไม่ถูกลบทุกสถานะในสาขาที่ดูแล รวมห้องในสาขาที่ปิดใช้งาน · กรองด้วยสาขา ประเภทห้อง ประเภทการเข้าพัก ช่วงราคา (ส่งวันที่มาได้และถูกตรวจรูปแบบ แต่ไม่มีผลกรอง) · ไม่มีรายการสิ่งอำนวยความสะดวกแนบมา
- ห้องคนละสาขา → ไม่มีสิทธิ์ · ห้องไม่มีจริง → ไม่พบข้อมูล
- สำเร็จ → มีบันทึกผูกกับสาขาของห้อง
- เทสที่มี: room/amenities_test.go (6 เทสฝั่งแอดมิน), room/closed_test.go ข้อแอดมินยังจัดการห้องในสาขาที่ปิดได้

AC-20: นัดหมายทำสัญญา
- ตั้งนัดบนใบรายเดือน → สำเร็จ และเขียนทับนัดเดิมได้ทุกครั้ง
- เวลานัดอ่านไม่ออก → ข้อมูลไม่ถูกต้อง (ตรวจก่อนหาใบจอง)
- ตั้งนัดบนใบรายวัน → "วันนัดหมายทำสัญญาใช้ได้เฉพาะการจองรายเดือน"
- เวลานัดรับแบบมีเขตเวลา หรือแบบวันที่และเวลาที่ไม่มีเขตเวลา (ถือเป็นเวลาไทย) → ไม่อยู่ในอนาคต → ข้อมูลไม่ถูกต้อง

- สำเร็จ → member ได้แจ้งเตือน "นัดหมายทำสัญญา" พร้อมรหัสจองและวันเวลาในรูปแบบ วว-ดด-ปปปป ชม:นาที และมีบันทึกในประวัติ
- [ช่องว่าง] วันเวลาในแจ้งเตือนแสดงตามเขตเวลาที่ส่งมา → ตั้งนัด 03:00 เวลาสากล → ข้อความขึ้น 03:00 ไม่ใช่ 10:00 เวลาไทย
- เทสที่มี: ยังไม่มีเทส

AC-21: ข้อผิดพลาดมีรูปแบบเดียวทั้งระบบ
- ข้อผิดพลาดทุกกรณีมีรหัสภาษาอังกฤษ ข้อความภาษาไทย และรายละเอียดรายช่องเฉพาะกรณีข้อมูลไม่ถูกต้อง
- รหัสข้อผิดพลาดมีแค่ 13 แบบ ความหมายที่ใช้ในเอกสารนี้
  - ยังไม่ได้เข้าสู่ระบบ ("กรุณาเข้าสู่ระบบ") = unauthorized
  - ไม่มีสิทธิ์ ("คุณไม่มีสิทธิ์เข้าถึงส่วนนี้") = forbidden
  - ไม่พบข้อมูล ("ไม่พบข้อมูลที่ต้องการ") = not_found
  - ข้อมูลมีอยู่แล้ว ("ข้อมูลนี้มีอยู่ในระบบแล้ว") = conflict
  - คำขอผิดรูปแบบ = bad_request
  - ข้อมูลไม่ถูกต้อง ("ข้อมูลที่กรอกไม่ถูกต้อง" + รายละเอียดรายช่อง) = validation_failed
  - เรียกผิดวิธี = method_not_allowed
  - เกิดข้อผิดพลาดภายในระบบ = internal_error
  - อีเมลหรือรหัสผ่านไม่ถูกต้อง = invalid_credentials
  - บัญชีถูกระงับ = account_disabled
  - ห้องไม่ว่าง = room_unavailable
  - สถานะปัจจุบันทำรายการนี้ไม่ได้ = invalid_state
  - ถูกจำกัดความถี่ (บอกเวลาที่ต้องรอเสมอ) = too_many_requests
- คำขอผิดรูปแบบ คือ ข้อมูลอ่านไม่ออกหรือชนิดผิด, รหัสอ้างอิงผิดรูปแบบ, ตัวกรองผิดรูปแบบ, ไฟล์ผิดหรือใหญ่เกิน, ข้อความในฟอร์มไม่ใช่ UTF-8
- รหัสอ้างอิงทุกชนิดขึ้นต้นด้วยชื่อตาราง เช่น brn-001 สำหรับสาขา · ตัวพิมพ์เล็กใหญ่ไม่มีผลและตัดศูนย์นำหน้าให้เอง · ตัวเลขเปล่า รหัสของตารางอื่น หรือเลขไม่เกิน 0 → คำขอผิดรูปแบบ
- ข้อมูลไม่ถูกต้อง คือ ค่าถูกชนิดแต่ผิดกติกา หรือส่งช่องที่ระบบไม่รู้จักมา
- ไม่ได้ล็อกอินหรือ token ใช้ไม่ได้ → ยังไม่ได้เข้าสู่ระบบ · ล็อกอินแล้วแต่บทบาทไม่พอ → ไม่มีสิทธิ์
- ชนข้อมูลซ้ำที่ระบบไม่ได้ดักไว้เอง → ข้อมูลมีอยู่แล้ว
- [ช่องว่าง] อ้างถึงข้อมูลที่ไม่มีอยู่จริงในบางจุด → ไม่ถูกแปลง กลายเป็นข้อผิดพลาดภายในระบบ (ต้นเหตุของ AC-18, AC-19, AC-26)
- เทสที่มี: httpx/errorenvelope_test.go (8 เทส)

AC-22: เวลาและวันที่
- เวลาทุกจุดเก็บเป็นเวลาสากล ส่วนวันที่ล้วน (วันเข้าพัก วันเช็คเอาท์ วันเข้าอยู่ วันทำสัญญา) เก็บเป็นวันที่
- "วันนี้ อดีต อนาคต" ของวันเข้าพักและวันเข้าอยู่ตัดสินด้วยปฏิทินไทยเสมอ ไม่ขึ้นกับเขตเวลาของเครื่อง → server ที่ตั้งเวลาสากลยังรับจอง "วันนี้" ตอนตีครึ่งเวลาไทยได้
- เวลาโอนและเวลานัดที่ไม่ระบุเขตเวลา → ถือเป็นเวลาไทย · ระบุมา → ใช้ตามนั้น
- การตรวจว่าเวลาโอนและเวลานัดอยู่ในอนาคตเทียบเป็นเวลาจริง ไม่ใช่เทียบวันที่
- วันเข้าอยู่ตั้งต้นของการค้นหา (AC-12) ใช้วันนี้ตามนาฬิกาของฐานข้อมูล จึงขึ้นกับเขตเวลาของฐานข้อมูล (docker ตั้งเป็นเวลาไทย)
- [ยังไม่ยืนยัน] เวลาที่ส่งกลับมีเขตเวลาตามเครื่องที่รัน backend (docker ตั้งเป็นเวลาไทย) · วันที่ล้วนส่งกลับเป็นเที่ยงคืนเวลาสากล ไม่ใช่วันที่เปล่า
- เทสที่มี: timex/timex_test.go (11 เทส)

  - ลิงก์ชี้ไปหน้าเว็บด้วยค่า env ตัวใหม่ แยกจากที่อยู่ของ backend
  - ตั้งรหัสใหม่สำเร็จ → ยกเลิก refresh token ทุกใบ และมีบันทึกการรีเซ็ตรหัสผ่าน
  - โหมด production แต่ไม่ได้ตั้งค่าระบบส่งอีเมล → ระบบไม่ยอมเริ่มทำงาน

AC-24: เข้าสู่ระบบด้วย Google หรือ Facebook
- รองรับ Google และ Facebook (ฐานข้อมูลจำกัดไว้) → เจ้าที่ตั้งค่ารหัสไม่ครบถูกปิดเงียบ ๆ โดยระบบไม่ล้ม
- ดูรายชื่อเจ้าที่เปิดอยู่ได้ เรียง Google ก่อน Facebook
- เริ่มล็อกอิน → เจ้าที่ปิดอยู่ → ไม่พบข้อมูล · เปิดอยู่ → ระบบฝากค่ายืนยันไว้ในเบราว์เซอร์ (อายุ 10 นาที ตั้งให้ปลอดภัยเฉพาะ production) แล้วพาไปหน้ายินยอมของเจ้านั้น · Google บังคับให้เลือกบัญชีทุกครั้ง
- กลับมาจากหน้ายินยอม → ล้างค่ายืนยันทิ้ง แล้วพากลับไปหน้าเว็บที่ตั้งไว้เสมอ
  - สำเร็จ → หน้าเว็บได้รหัสใช้ครั้งเดียวอายุ 2 นาที ไปแลกเป็นการล็อกอินจริง
  - ผู้ใช้กดยกเลิก, ค่ายืนยันไม่ตรงหรือไม่มี, ไม่ได้รหัสจากเจ้านั้น, เจ้านั้นไม่ส่งอีเมล, อีเมลยังไม่ยืนยัน (Facebook ถือว่ายืนยันแล้วถ้าส่งอีเมลมา), เชื่อมต่อไม่สำเร็จ, บัญชีถูกระงับ → หน้าเว็บได้ข้อความภาษาไทยบอกสาเหตุ
- การจับคู่บัญชี (ทำในธุรกรรมเดียว)
  - เคยผูกบัญชีภายนอกนี้แล้ว → เข้าบัญชีเดิม โดยจับคู่จากรหัสผู้ใช้ของเจ้านั้น ไม่ใช่อีเมล
  - ไม่เคยผูก แต่มีบัญชีอีเมลเดียวกันที่ยังไม่ถูกลบ → ผูกเข้ากับบัญชีนั้น ทุกบทบาทรวมผู้ดูแล
  - ไม่มีทั้งคู่ → สร้าง member ใหม่ที่ยังไม่มีรหัสผ่านและยังไม่มีเบอร์ ชื่อมาจากเจ้านั้น (ถ้าไม่มีใช้ส่วนหน้าเครื่องหมาย @ ของอีเมล)
- ทั้งสามทางมีบันทึกในประวัติพร้อมชื่อเจ้า และบันทึกเวลาเข้าสู่ระบบล่าสุด
- [ช่องว่าง] อีเมลตรงกับบัญชีผู้ดูแลที่ถูกลบ → หาบัญชีไม่เจอแต่สร้างใหม่ไม่ได้เพราะอีเมลซ้ำ → หน้าเว็บได้ข้อความ "ข้อมูลนี้มีอยู่ในระบบแล้ว"
- แลกรหัสใช้ครั้งเดียว → สำเร็จได้การล็อกอิน · รหัสว่าง ไม่มีจริง หมดอายุ หรือใช้แล้ว → "ลิงก์เข้าสู่ระบบหมดอายุแล้ว กรุณาลองใหม่อีกครั้ง" · บัญชีถูกระงับ → บัญชีถูกระงับ · ฐานข้อมูลเก็บแค่ค่า hash
- บัญชีที่ยังไม่มีรหัสผ่านตั้งรหัสครั้งแรกได้โดยไม่ต้องกรอกรหัสเดิม · ตั้งแล้วครั้งถัดไปต้องกรอกรหัสเดิมตามปกติ
- บัญชีที่สร้างผ่าน Google/Facebook ไม่มีเบอร์ → ต้องกรอกเบอร์ก่อนถึงจะแก้โปรไฟล์ได้
- ฐานข้อมูลห้ามปักธงให้ต้องเปลี่ยนรหัสกับบัญชีที่ยังไม่มีรหัส
- [ช่องว่าง] ไฟล์ตัวอย่าง env ตั้งรหัสของ Google เป็นข้อความ "..." ซึ่งไม่ว่าง → คัดลอกไปใช้ตรง ๆ แล้ว Google ถูกนับว่าเปิดอยู่ทั้งที่ไม่มีรหัสจริง · และตั้งหน้าที่พากลับไปผิดเป็นหน้าตรวจสุขภาพของ backend

AC-26: จัดการรายละเอียดสาขา

- แก้รายละเอียดสาขาเป็นการแทนที่ทั้งชุด: ชื่อ คำโปรย คำอธิบาย ที่อยู่ เบอร์ LINE อีเมล พิกัด ลิงก์แผนที่ จำนวนอาคาร จำนวนชั้น ราคาเริ่มต้นรายวัน ช่วงราคารายเดือน ค่าน้ำ ค่าไฟ เงินประกัน ค่าล่วงหน้า ค่าทำสัญญา รูปปก → สำเร็จได้สาขาพร้อมรูป สิ่งอำนวยความสะดวก และสถานที่ใกล้เคียง
  - ชื่อบังคับและยาวไม่เกิน 200 · จำนวนอาคารและชั้นมากกว่า 0 · ค่าน้ำค่าไฟไม่ติดลบ · ราคารายเดือนต่ำสุดไม่เกินสูงสุด · รูปปกต้องเป็นลิงก์ http(s) → ผิดข้อใด → ข้อมูลไม่ถูกต้อง
  - ไม่ส่งพิกัดหรือราคา → ค่าเดิมถูกล้าง · ไม่ส่งรูปปก → คงรูปเดิม · ส่งรายการเบอร์ว่าง → เบอร์ถูกล้าง
  - [ช่องว่าง] [ยังไม่ยืนยัน] ไม่ส่งรายการเบอร์เลย → น่าจะเกิดข้อผิดพลาดภายในระบบ เพราะช่องเบอร์ในฐานข้อมูลห้ามว่าง
  - [ช่องว่าง] ค่าทำสัญญา เงินประกัน ค่าล่วงหน้า ติดลบได้ → ค่าทำสัญญา -500 ทำให้ใบจองรายเดือนใหม่มียอด -500 · อีเมล เบอร์ และลิงก์แผนที่ไม่ถูกตรวจรูปแบบ
  - แก้สาขาที่ปิดใช้งานได้ตามปกติ
- ตั้งสิ่งอำนวยความสะดวกของสาขาเป็นการแทนที่ทั้งชุด → สำเร็จได้รายการใหม่
  - [ช่องว่าง] ไม่ได้ทำในธุรกรรมเดียวและไม่แปลงข้อผิดพลาด → รหัสที่ไม่มีจริง → ข้อผิดพลาดภายในระบบ · รหัสซ้ำ → ข้อมูลมีอยู่แล้ว · ทั้งสองกรณีรายการเดิมถูกลบไปแล้ว

  - รายการใดไม่มีชื่อ → "รายการที่ N ยังไม่ได้กรอกชื่อสถานที่" · ลำดับเป็น 0 → ใช้ลำดับในรายการที่ส่งมาแทน · ไม่ส่งรายการเลย → ลบทั้งหมด

- super admin ดูรายการสาขาทั้งหมดรวมที่ปิดใช้งานได้
- ดูรายละเอียดสาขาด้วยรหัสสาขาหรือชื่อย่อ เช่น prachauthit-45 → ค่าที่ไม่ใช่รหัสถือเป็นชื่อย่อ → ไม่เจอ → ไม่พบข้อมูล
- ดูสาขาที่ปิดใช้งาน → ไม่พบข้อมูลทั้งทางรหัสและชื่อย่อ · ปิดสาขาหนึ่งไม่กระทบสาขาอื่น
- รายการสิ่งอำนวยความสะดวกกลาง → ทั้งหมด เรียงตามลำดับแล้วตามชื่อ
- รายการประเภทห้อง → กรองตามสาขาได้ (ไม่กรองจะเห็นทุกสาขาปนกัน) เรียงตามลำดับแล้วตามชื่อ · รหัสสาขาผิดรูปแบบ → คำขอผิดรูปแบบ
- ดูรายละเอียดห้อง → ได้ห้องพร้อมสิ่งอำนวยความสะดวกและแกลเลอรี · ห้องไม่มีจริง ถูกลบ หรืออยู่ในสาขาที่ปิด → ไม่พบข้อมูล
- [ช่องว่าง] ห้องที่มีผู้เช่าหรือปิดปรับปรุง → ยังดูรายละเอียดได้ตามปกติ ไม่ได้บอกว่าจองไม่ได้
- เทสที่มี: branch/closed_test.go (4 เทส), room/closed_test.go (2 เทส), room/amenities_test.go (2 เทส)

AC-28: รายชื่อสมาชิกและประวัติรายคน (Admin และ Super Admin)
- รายชื่อสมาชิก → สมาชิกที่ยังไม่ถูกลบทั้งระบบ ค้นได้จากชื่อ นามสกุล อีเมล เบอร์ เรียงคนสมัครล่าสุดก่อน → admin และ super admin เห็นเหมือนกัน
- ประวัติการจองของสมาชิกรายคน → admin เห็นเฉพาะใบในสาขาตัวเอง · super admin เห็นทุกสาขา และเลือกดูสาขาเดียวไม่ได้
  - รหัสสมาชิกผิดรูปแบบ → คำขอผิดรูปแบบ · ไม่มีจริงหรือไม่ใช่สมาชิก → ได้รายการว่าง (ไม่ตรวจว่ามีผู้ใช้จริง)
- รายการจองของแอดมิน → ค้นได้จากรหัสจอง เลขห้อง ชื่อและนามสกุลเจ้าของบัญชี (ไม่ค้นอีเมลและชื่อผู้เข้าพัก) · กรองสถานะ "ทั้งหมด" = ไม่กรอง · สถานะหรือประเภทที่ไม่รู้จัก → คำขอผิดรูปแบบ · เรียงใหม่สุดก่อน
- ทุกใบในรายการมีชื่อสาขา เลขห้อง ชื่อและอีเมลเจ้าของบัญชี และมีการแจ้งชำระล่าสุดเฉพาะใบที่ไม่ใช่รอชำระเงิน
- เทสที่มี: ยังไม่มีเทส

AC-29: โปรไฟล์ของตัวเอง
- ดูโปรไฟล์ → ได้ข้อมูลผู้ใช้ รวมธงต้องเปลี่ยนรหัส สถานะเปิดใช้งาน เวลาเข้าสู่ระบบล่าสุด และสาขา (ถ้าเป็น admin) โดยไม่มีรหัสผ่าน
- แก้โปรไฟล์ด้วยชื่อ นามสกุล เบอร์ และรูปโปรไฟล์ → ชื่อ นามสกุล เบอร์ บังคับตามกติกา AC-1 · ไม่ส่งรูปโปรไฟล์ → คงเดิม · มีบันทึกในประวัติ
- [ช่องว่าง] รูปโปรไฟล์ไม่ถูกตรวจเลย → ลิงก์ javascript ถูกบันทึกได้ (ช่องรูปอื่นในระบบมีการตรวจ ดู AC-14)
- เปลี่ยนรหัสผ่าน → สำเร็จได้ข้อความ "เปลี่ยนรหัสผ่านเรียบร้อยแล้ว กรุณาเข้าสู่ระบบใหม่" ปลดธงต้องเปลี่ยนรหัส และมีบันทึกในประวัติ
  - บัญชีที่มีรหัสแล้วแต่ไม่กรอกรหัสเดิม → ข้อมูลไม่ถูกต้องที่ช่องรหัสเดิม
  - รหัสใหม่ซ้ำรหัสเดิม → "รหัสผ่านใหม่ต้องไม่ซ้ำกับรหัสผ่านเดิม"
  - ยืนยันรหัสไม่ตรง → "รหัสผ่านยืนยันไม่ตรงกัน"
  - รหัสใหม่ไม่ผ่านกติกา AC-1 → ข้อมูลไม่ถูกต้อง
  - รหัสเดิมไม่ถูกต้อง → "รหัสผ่านเดิมไม่ถูกต้อง" (ตรวจหลังข้อข้างบนผ่านหมดแล้วเท่านั้น)
- เทสที่มี: account/oauth_test.go ข้อตั้งรหัสครั้งแรก และข้อยังต้องกรอกรหัสเดิมหลังตั้งแล้ว

## Acceptance Criteria — หน้าเว็บ

AC-30: การคุยกับระบบหลังบ้านและการเก็บการล็อกอิน
- ทุกการเรียกระบบหลังบ้านผ่านตัวกลางเดียว ไม่มีหน้าไหนเรียกเอง
- ที่อยู่ของระบบหลังบ้านมาจาก env ของหน้าเว็บ ไม่ตั้ง → ใช้ localhost:8080
- มีการล็อกอินอยู่ → แนบ token ไปทุกคำขอ รวมคำขอสาธารณะ
- ตัวกรองที่ว่างไม่ถูกส่งไป
- ระบบหลังบ้านตอบข้อผิดพลาด → ใช้ข้อความภาษาไทยจากระบบหลังบ้านก่อน ถ้าไม่มีใช้ข้อความสำรองตามรหัส (มี 12 รหัส ขาดกรณีถูกจำกัดความถี่) ถ้าไม่รู้จักอีกใช้ "เกิดข้อผิดพลาด กรุณาลองใหม่"
- ได้คำตอบที่ไม่ใช่ข้อมูลของระบบ (เช่นหน้า error ของ proxy) → "เกิดข้อผิดพลาดที่เซิร์ฟเวอร์ กรุณาลองใหม่"
- ติดต่อระบบหลังบ้านไม่ได้เลย → "เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ กรุณาตรวจสอบอินเทอร์เน็ตแล้วลองใหม่" · ถูกยกเลิกกลางทางเพราะเปลี่ยนหน้า → เงียบ ไม่แสดงอะไร
- การล็อกอินเก็บในเบราว์เซอร์ 3 อย่าง: access token, refresh token, ข้อมูลผู้ใช้ → ล็อกอินหรือออกแล้วทุกส่วนของหน้ารู้ทันที และซิงก์ข้ามแท็บ
- ข้อมูลผู้ใช้ที่เก็บไว้เสีย → ถือว่าไม่มีผู้ใช้ แทนที่ทั้งเว็บจะพัง
- "ล็อกอินอยู่" ดูแค่ว่ามี access token เก็บไว้ ไม่ได้ดูว่าหมดอายุหรือยัง
- [ช่องว่าง] ไม่มีการต่ออายุการล็อกอิน → ผ่านไป 30 นาทีทุกหน้าที่ต้องล็อกอินขึ้นข้อผิดพลาด ขณะที่เมนูยังบอกว่าล็อกอินอยู่ ต้องกดออกแล้วเข้าใหม่เอง (refresh token ถูกเก็บไว้แต่ใช้แค่ตอนออกจากระบบ)
- [ช่องว่าง] บทบาทและชื่อที่ใช้ในหน้าเว็บมาจากข้อมูลที่เก็บตอนล็อกอิน → super admin ย้ายสาขาหรือแก้ชื่อให้ หน้าเว็บยังแสดงค่าเดิมจนกว่าจะล็อกอินใหม่
- ทุกส่วนที่ดึงข้อมูลมีสถานะกำลังโหลด ผิดพลาด และลองใหม่ได้ · เปลี่ยนตัวกรองหรือออกจากหน้าระหว่างโหลด → คำขอเดิมถูกยกเลิก
- เทสที่มี: ยังไม่มีเทส

AC-31: หน้าต่าง ๆ และโครงหน้า
- โซนผู้ใช้ทั่วไปมีแถบเมนู 4 เมนู "หน้าหลัก / สาขาของเรา / ค้นหาห้องพัก / ติดต่อเรา" และส่วนท้าย ประกอบด้วยหน้า
  - หน้าแรก (/) ดู AC-32
  - สาขาในเครือทั้งหมด (/branches) และรายละเอียดสาขาแท็บรูปภาพกับแท็บแผนที่ (/branches/ชื่อสาขา และ /branches/ชื่อสาขา/map) ดู AC-33
  - ค้นหาห้องพัก (/rooms) ดู AC-34
  - รายละเอียดห้อง (/rooms/รหัสห้อง) ยังเป็นหน้า "กำลังอยู่ระหว่างพัฒนา"
  - ติดต่อเรา (/contact) ดู AC-35
  - เข้าสู่ระบบ (/login) และสมัครสมาชิก (/register) ดู AC-36
  - ที่อยู่อื่นทั้งหมด → หน้า "ไม่พบหน้าที่ต้องการ"
- หน้าเข้าสู่ระบบผู้ดูแล (/admin/login) มีแค่โลโก้ด้านบน ไม่มีส่วนท้าย ดู AC-37
- หน้าของ admin (/admin) ต้องเป็น admin → ยังเป็นหน้า "ระบบผู้ดูแลระบบ กำลังอยู่ระหว่างพัฒนา" มีปุ่มออกจากระบบ
- หน้าของ super admin ต้องเป็น super admin ใช้โครงหน้าแบบมีเมนูด้านข้าง → แดชบอร์ด (/superadmin) และจัดการผู้ดูแล (/superadmin/staff) ทำแล้ว · จัดการสาขาและประวัติการใช้งานยังเป็นหน้ากำลังพัฒนา
- หน้ากำลังพัฒนาทุกหน้ามีหัวข้อ ข้อความ "หน้านี้กำลังอยู่ระหว่างพัฒนา" และปุ่มกลับหน้าหลัก
- [ช่องว่าง] ยังไม่มีหน้ารับผลการล็อกอินผ่าน Google/Facebook (AC-24) และหน้าใบจองที่ลิงก์ในแจ้งเตือนชี้ไป (AC-5) → ทั้งสองตกไปหน้า "ไม่พบหน้าที่ต้องการ"
- เทสที่มี: frontend/src/App.test.js (หน้าแรกมีหัวข้อหลัก, เมนูครบ 4 รายการ)

AC-32: หน้าแรก
- ดึงรายการสาขาครั้งเดียวแล้วใช้ร่วมกันทั้งส่วนสาขาของเราและส่วนประเภทห้องพัก · หน้าเว็บกรองเฉพาะสาขาที่เปิดใช้งานซ้ำอีกชั้น
- ส่วนหัว: หัวข้อ "หอพักวิเศษสุขนคร คอนโด" ปุ่ม "ค้นหาห้องพัก" และ "ดูสาขาทั้งหมด" · สไลด์รูปสุ่ม 15 รูปจากรายการไฟล์รูปที่เขียนไว้ในหน้าเว็บ สุ่มครั้งเดียวตอนเข้าหน้า เลื่อนเองทุก 5 วินาทีวนไม่รู้จบ · กดเลื่อนเอง → เริ่มนับเวลาใหม่
- แถบสิ่งอำนวยความสะดวกเป็นข้อความคงที่ 4 ช่อง "คีย์การ์ด / รปภ. 24 ชั่วโมง / ที่จอดรถ / ห้องน้ำในตัว" ไม่ได้มาจากระบบหลังบ้าน
- สาขาของเรา: การ์ดละสาขามีรูปปก ชื่อ ที่อยู่ → กดแล้วไปหน้ารายละเอียดสาขา
- รูปปกสาขา = รูปปกจากระบบหลังบ้านถ้ามี ไม่มี → รูปแรกในรายการไฟล์ของสาขานั้น (ดู AC-33) · ไม่มีทั้งคู่หรือโหลดรูปไม่ขึ้น → ไอคอนอาคารแทน
- ประเภทห้องพัก
  - การ์ดรายวันแสดงเมื่อมีสาขาที่มีราคารายวันมากกว่า 0 → "ราคาเริ่มต้น (ค่าต่ำสุด) บาท/คืน" กดแล้วไปหน้าค้นหาที่เลือกรายวันไว้
  - การ์ดรายเดือนแสดงเมื่อมีสาขาที่มีราคารายเดือนมากกว่า 0 → "ราคา (ต่ำสุด) - (สูงสุด) บาท/เดือน" กดแล้วไปหน้าค้นหาที่เลือกรายเดือนไว้
  - ไม่มีทั้งคู่ → "ยังไม่มีข้อมูลราคาห้องพัก"
- ส่วนท้ายหน้า: ยังไม่ล็อกอิน → ปุ่มเข้าสู่ระบบและสมัครสมาชิก · ล็อกอินแล้ว → ปุ่มค้นหาห้องพัก
- ราคาแสดงแบบมีคั่นหลักพัน ไม่มีทศนิยม · ไม่มีค่า → ขีด
- ทุกส่วนที่ดึงข้อมูลมีสถานะกำลังโหลด (โครงกระพริบ) ผิดพลาด (ข้อความ + ปุ่มลองใหม่) ว่าง และสำเร็จ
- เทสที่มี: frontend/src/App.test.js ข้อหัวข้อหลัก

AC-33: หน้ารวมสาขาและรายละเอียดสาขา
- หน้ารวมสาขาแสดงสาขาที่เปิดอยู่เป็นแถว: รูปปก ชื่อ ที่อยู่ เบอร์ LINE ป้ายไฮไลต์ไม่เกิน 3 ป้าย คำโปรย ข้อความสถานะห้อง และปุ่ม "ดูรายละเอียด →"
  - ป้ายแรกคือ "N อาคาร N ชั้น" ตามด้วยสิ่งอำนวยความสะดวกของสาขาตามลำดับ ใกล้ร้านสะดวกซื้อ, มีที่จอดรถ, มีลิฟต์, มีเฟอร์นิเจอร์ครบครัน, เครื่องซักผ้าหยอดเหรียญ, มีไวไฟ, แอร์ทุกห้อง
  - [ช่องว่าง] ป้าย "มีลิฟต์" ผูกกับรหัส elevator แต่ข้อมูลจริงใช้รหัส lift → ไม่มีสาขาไหนได้ป้ายนี้
  - ข้อความสถานะห้องตัดสินจากว่ามีข้อมูลราคาส่งมาหรือไม่ ไม่ใช่ดูว่ามากกว่า 0: มีทั้งสองแบบ → "มีห้องพักทั้งรายวัน และรายเดือน" · มีแค่รายเดือน → "มีห้องพักรายเดือนพร้อมเข้าพัก" · มีแค่รายวัน → "มีห้องพักรายวันพร้อมเข้าพัก" · ไม่มีเลย → "ติดต่อสอบถามห้องว่าง"
- หน้ารายละเอียดสาขาเปิดได้ทั้งด้วยชื่อย่อและรหัสสาขา
  - รหัสผิดรูปแบบ → "รหัสสาขาไม่ถูกต้อง" ไม่มีปุ่มลองใหม่ · ไม่พบหรือสาขาปิด → "ไม่พบสาขาที่ต้องการ" · อื่น ๆ → ข้อความจากระบบหลังบ้าน
  - แท็บรูปภาพกับแผนที่เปลี่ยนที่อยู่หน้า → เปิดที่อยู่ของแท็บแผนที่ตรง ๆ → แท็บแผนที่ถูกเลือกทันที
  - [ช่องว่าง] แกลเลอรีไม่ได้ใช้รูปจากระบบหลังบ้าน แต่ใช้รายการไฟล์ที่เขียนไว้ในหน้าเว็บตามชื่อย่อสาขา (บางแค 45 รูป เริ่มที่รูปที่ 23 · เจริญกรุงเพลส 44 รูป เริ่มที่รูปที่ 41 · ประชาอุทิศ 45 15 รูป) → รูปที่แอดมินอัปโหลดไม่โผล่ และสาขาใหม่ → "ยังไม่มีรูปภาพสำหรับสาขานี้"
  - แผนที่เลือกตามลำดับ: ลิงก์แผนที่จากระบบหลังบ้าน → พิกัดที่เขียนไว้ในหน้าเว็บของ 3 สาขา → ค้นจากที่อยู่ · ลิงก์ "เปิดหน้าสถานที่เต็มใน Maps" ใช้ลิงก์แผนที่ → ลิงก์สถานที่ที่เขียนไว้ → ลิงก์เดียวกับแผนที่ · ลิงก์แผนที่ที่ฝังในหน้าไม่ได้ → แสดงปุ่ม "เปิดใน Google Maps" แทน
  - [ช่องว่าง] พิกัดของสาขาจากระบบหลังบ้านไม่ถูกใช้เลย ใช้พิกัดที่เขียนไว้ในหน้าเว็บแทน
  - การ์ดราคารายวันและรายเดือนใช้กติกา "มีข้อมูลหรือไม่" แบบเดียวกับหน้ารวม → ไม่มีประเภทนั้น → "ไม่มีห้องพักรายวัน" หรือ "ไม่มีห้องพักรายเดือน" · ไม่มีทั้งคู่ → ไม่แสดงการ์ด
  - การ์ดรายละเอียดเพิ่มเติม: เงินประกัน (มีเงินประกัน → "N บาท" · ไม่งั้นมีค่าล่วงหน้า → "จ่ายล่วงหน้า N บาท" · ไม่งั้น → ข้อความคงที่ "จ่ายล่วงหน้า 3 เดือนของราคาห้องพัก"), ค่าน้ำ, ค่าไฟ, ที่จอดรถ (มีสิ่งอำนวยความสะดวกที่จอดรถ → "มีที่จอดรถ" ไม่งั้น "ไม่มีที่จอดรถ"), "N ตึก N ชั้น/ตึก"
  - [ช่องว่าง] ข้อมูลตั้งต้นทุกสาขาไม่มีเงินประกันและค่าล่วงหน้า → ทุกสาขาแสดงข้อความคงที่ "จ่ายล่วงหน้า 3 เดือนของราคาห้องพัก" ที่ไม่ได้มาจากข้อมูลจริง
  - ปุ่ม "จองห้องพัก" → หน้าค้นหาที่เลือกสาขานี้ไว้ · ปุ่มที่สอง: มี LINE → "แอดไลน์ (LINE ID)" เปิดหน้าเพิ่มเพื่อนของ LINE (เติม @ ให้ถ้าไม่มี) · ไม่มี LINE แต่มีเบอร์ → โทรเบอร์แรก · ไม่มีทั้งคู่ → หน้าติดต่อเรา
  - การ์ดสิ่งอำนวยความสะดวกใช้ของสาขา ไอคอนเลือกจากข้อมูลไอคอน (รู้จัก 12 แบบ ที่เหลือใช้ไอคอนสำรอง) · ว่าง → "ยังไม่มีข้อมูลสิ่งอำนวยความสะดวกสำหรับสาขานี้"
  - สถานที่ใกล้เคียงจัดกลุ่มตามหมวด สถานศึกษา / โรงพยาบาล / ห้างสรรพสินค้าและแหล่งช้อปปิ้ง / สวนสาธารณะ หมวดอื่นแสดงตามที่บันทึก เรียงในกลุ่มตามลำดับ
  - "สาขาอื่นๆ ของเรา" แสดงสาขาที่เปิดอยู่อื่นไม่เกิน 2 สาขา ไม่มี → ไม่แสดงส่วนนี้

AC-34: หน้าค้นหาห้องพัก
- ตัวกรอง 3 ตัว: สาขา (มี "ทุกสาขา"), ประเภท (ทุกประเภท / รายวัน / รายเดือน ซึ่งคือประเภทการเข้าพัก ไม่ใช่ประเภทห้อง), วันที่
- ค่าตัวกรองอ่านจากที่อยู่หน้าตอนเปิด และเขียนกลับลงที่อยู่หน้าทุกครั้งที่เปลี่ยน · เปลี่ยนตัวกรองใด ๆ → กลับไปหน้า 1 · เปลี่ยนประเภท → ล้างวันที่
- ตัวกรองวันที่
  - ยังไม่เลือกประเภท → ใช้ไม่ได้ ขึ้นว่า "เลือกประเภทก่อน"
  - รายวัน → เลือกเป็นช่วงสองคลิก (คลิกที่สองก่อนวันเริ่ม = เริ่มช่วงใหม่)
  - รายเดือน → เลือกวันเดียว
  - ปฏิทินเริ่มวันจันทร์ ป้ายแสดง วว/ดด/ปป เป็น พ.ศ. สองหลัก มีปุ่ม "ล้างวันที่"
- ส่งตัวกรองไปค้นหา: สาขา ประเภท หน้า · รายวันส่งวันเข้าพักและวันเช็คเอาท์ · รายเดือนส่งวันเข้าอยู่ · ไม่ส่งขนาดหน้า (ได้หน้าละ 20) และไม่ได้ใช้ตัวกรองประเภทห้องหรือราคา
- [ช่องว่าง] เลือกวันออกเป็นวันเดียวกับวันเข้าได้ → ระบบหลังบ้านปฏิเสธ → หน้าขึ้นข้อผิดพลาด "ข้อมูลที่กรอกไม่ถูกต้อง" แทนที่จะกันไว้ที่ปฏิทิน · เลือกวันในอดีตได้ด้วย
- ตัวกรองในที่อยู่หน้าผิดรูปแบบ → "เงื่อนไขค้นหาไม่ถูกต้อง" · ไม่พบห้อง → "ไม่พบห้องพักที่ตรงกับเงื่อนไขที่เลือก ลองปรับตัวกรองแล้วค้นหาใหม่อีกครั้ง"
- การ์ดห้อง: หัวข้อ "ห้องพักรายวัน" หรือ "ห้องพักรายเดือน", ชื่อสาขา, ป้าย, ราคาต่อวันหรือต่อเดือน, "ค่าน้ำ N บาท/ยูนิต, ค่าไฟ N บาท/ยูนิต", ปุ่ม "จองเลย"
  - รูปการ์ด = รูปปกของห้อง ไม่มี → ไอคอนอาคาร (ไม่ใช้รูปสาขาแทน)
  - ป้าย = ประเภทห้อง, ขนาด "N ตร.ม." แล้วตามด้วยสิ่งอำนวยความสะดวกทั้งหมดของสาขา
  - [ช่องว่าง] ระบบหลังบ้านส่งสิ่งอำนวยความสะดวกของห้องมาให้แล้ว (AC-12) แต่หน้าเว็บยังใช้ของสาขา → ห้องที่ไม่มีแอร์ก็ขึ้นป้ายเครื่องปรับอากาศถ้าสาขามี
  - ไม่แสดงเลขห้อง อาคาร และชั้น
- กด "จองเลย": ยังไม่ล็อกอิน → กล่อง "โปรดลงทะเบียน / เข้าสู่ระบบ เพื่อทำการจอง" พร้อมปุ่มไปหน้าเข้าสู่ระบบและสมัครสมาชิก (ปิดได้ด้วยคลิกนอกกล่อง ปุ่ม Esc หรือปุ่ม X) · ล็อกอินแล้ว (ทุกบทบาท) → ไปหน้ารายละเอียดห้องที่ยังกำลังพัฒนา
- แบ่งหน้าด้วยปุ่มก่อนหน้าและถัดไป พร้อม "หน้า X จาก Y" · เปลี่ยนหน้า → เลื่อนขึ้นบนสุด
- เทสที่มี: ยังไม่มีเทส

AC-36: สมัครสมาชิกและเข้าสู่ระบบของสมาชิก
- ล็อกอินอยู่แล้วเปิดหน้าเข้าสู่ระบบหรือสมัครสมาชิก → ถูกพากลับหน้าแรกทันที (ทุกบทบาท)
- หน้าเข้าสู่ระบบตรวจก่อนส่ง: อีเมลว่าง → "กรุณากรอกอีเมล" · ไม่ใช่รูปแบบอีเมล → "รูปแบบอีเมลไม่ถูกต้อง" · รหัสว่าง → "กรุณากรอกรหัสผ่าน"
- เข้าสู่ระบบสำเร็จ → เก็บการล็อกอินแล้วพาไปหน้าแรกตามบทบาท: member → หน้าแรก, admin → หน้า admin, super admin → หน้า super admin
- เข้าสู่ระบบไม่สำเร็จ → แสดงข้อความจากระบบหลังบ้านเป็นแถบบนฟอร์ม เช่น "อีเมลหรือรหัสผ่านไม่ถูกต้อง" หรือข้อความถูกจำกัดความถี่ของ AC-2
- ช่อง "จดจำฉัน" ไม่มีผลอะไร (เก็บการล็อกอินในเบราว์เซอร์เสมอ)
- ลิงก์ "ลืมรหัสผ่าน?" → ไปหน้าติดต่อเรา (ดู AC-23)
- หน้าสมัครสมาชิกตรวจก่อนส่ง: ชื่อหรือนามสกุลว่าง, เบอร์ต้องเป็นตัวเลขล้วน 9 ถึง 10 หลัก, อีเมลแบบเดียวกับหน้าเข้าสู่ระบบ, รหัสผ่านยาว 8 ถึง 72 ตัวอักษร, ยืนยันรหัสต้องตรงกัน
- [ช่องว่าง] กติกาเบอร์ของหน้าเว็บเข้มกว่าระบบหลังบ้าน → เบอร์ 02-872-7800 ถูกหน้าเว็บปฏิเสธทั้งที่ระบบหลังบ้านรับ · ส่วนรหัสผ่านหน้าเว็บไม่ตรวจว่าต้องมีทั้งตัวอักษรและตัวเลข → ไปโดนระบบหลังบ้านปฏิเสธแทน
- สมัครสมาชิกส่งแค่ชื่อ นามสกุล เบอร์ อีเมล (ตัดช่องว่างหัวท้าย) และรหัสผ่าน ไม่ส่งช่องยืนยันรหัส → สำเร็จ → เก็บการล็อกอินแล้วไปหน้าแรก (ไม่แยกตามบทบาท) · ข้อมูลไม่ถูกต้อง → ข้อความแสดงใต้ช่องที่ผิด · ข้อผิดพลาดอื่น → แถบบนฟอร์ม
- เมนูด้านบนเปลี่ยนจากปุ่มเข้าสู่ระบบและสมัครสมาชิกเป็นปุ่ม "ออกจากระบบ" ทันทีที่ล็อกอิน (ไม่ต้องโหลดหน้าใหม่) · กดออกจากระบบ → แจ้งระบบหลังบ้านโดยไม่รอผล ล้างการล็อกอิน แล้วไปหน้าแรก
- เทสที่มี: ยังไม่มีเทส

AC-37: เข้าสู่ระบบผู้ดูแลและการกันหน้า
- หน้าเข้าสู่ระบบผู้ดูแลเหมือนหน้าของสมาชิก แต่ไม่มีลิงก์สมัครสมาชิก และท้ายการ์ดเขียนว่า "ลืมรหัสผ่าน? กรุณาติดต่อหัวหน้าผู้ดูแลระบบเพื่อรีเซ็ตรหัสผ่าน"
- ล็อกอินอยู่แล้วเปิดหน้านี้ → ถูกพาไปหน้าแรกของบทบาทที่ล็อกอินอยู่
- บัญชี member ล็อกอินที่หน้านี้ → ไม่เก็บการล็อกอิน และแสดง "บัญชีนี้ไม่มีสิทธิ์เข้าใช้ระบบผู้ดูแล กรุณาเข้าสู่ระบบที่หน้าสำหรับสมาชิก"
  - [ช่องว่าง] ระบบหลังบ้านออก refresh token และบันทึกการเข้าสู่ระบบให้ member คนนั้นไปแล้ว หน้าเว็บทิ้ง token โดยไม่แจ้งออกจากระบบ → refresh token ค้างใช้ได้อีก 30 วัน
- admin หรือ super admin ล็อกอินสำเร็จ → กลับไปหน้าที่ถูกกันไว้ก่อนหน้า ถ้าไม่มีไปหน้าแรกของบทบาท
- การกันหน้าอ่านจากข้อมูลที่เก็บในเบราว์เซอร์ จึงยังกันได้หลังโหลดหน้าใหม่
  - ยังไม่ล็อกอิน → ไปหน้าเข้าสู่ระบบผู้ดูแล โดยจำหน้าที่ตั้งใจจะเข้าไว้
  - ล็อกอินแล้วแต่บทบาทไม่ตรง → ไปหน้าแรกของบทบาทตัวเอง (member เปิดหน้า super admin → หน้าแรก · admin เปิดหน้า super admin → หน้า admin · super admin เปิดหน้า admin → หน้า super admin)
  - เป็นแค่ความสะดวกของผู้ใช้ สิทธิ์จริงถูกตรวจที่ระบบหลังบ้านทุกครั้ง (AC-4, AC-5)
- ออกจากระบบจากหน้า admin หรือเมนูด้านข้างของ super admin → แจ้งระบบหลังบ้านโดยไม่รอผล ล้างการล็อกอิน แล้วไปหน้าเข้าสู่ระบบผู้ดูแล
- [ช่องว่าง] ผู้ดูแลที่ถูกปักธงให้ต้องเปลี่ยนรหัส (เพิ่งถูกสร้างหรือถูกรีเซ็ต) → หน้าเว็บไม่บังคับเปลี่ยนรหัส และยังไม่มีหน้าเปลี่ยนรหัสให้ใช้
- เทสที่มี: ยังไม่มีเทส

AC-38: แดชบอร์ดหัวหน้าผู้ดูแลระบบ
- ข้อมูลทั้งหน้ามาจากแดชบอร์ดของ AC-25 ดึงครั้งเดียว
- หัวข้อ "แดชบอร์ด" และ "สรุปข้อมูลประจำวันที่ (วันที่ปัจจุบันของเครื่องผู้ใช้แบบไทย พ.ศ.)"
- การ์ดละสาขา 3 ช่อง: "ห้องว่างรายวันวันนี้" ว่าง/ทั้งหมด ห้อง · "ห้องว่างรายเดือนวันนี้" ว่าง/ทั้งหมด ห้อง · "รอตรวจสอบการจอง" รอตรวจ/ใบจองทั้งหมด รายการ
- กล่อง "กิจกรรมล่าสุด" บรรทัดละรายการ: "(บทบาท) (ชื่อสาขา) (การกระทำ)" และเวลาแบบ ปปปป-ดด-วว ชม:นาที ตามเขตเวลาของเครื่องผู้ใช้ · บทบาทแสดงเป็น สมาชิก / Admin / Superadmin · ไม่มีกิจกรรม → "ยังไม่มีกิจกรรมในระบบ"
- [ช่องว่าง] ตารางแปลการกระทำเป็นภาษาไทยมี 27 จาก 29 แบบ ขาดการเพิ่มและลบรูปแกลเลอรีห้อง → สองแบบนี้แสดงเป็นรหัสภาษาอังกฤษ
- เมนูด้านข้าง: ชื่อผู้ล็อกอินและบทบาท, เมนู "แดชบอร์ด / จัดการผู้ดูแลระบบ / จัดการสาขา / activity log", ปุ่ม Logout
- เทสที่มี: ยังไม่มีเทส

AC-39: จัดการผู้ดูแลระบบ
- ดึงรายชื่อผู้ดูแลและรายการสาขาทั้งหมดพร้อมกัน → ตาราง: ผู้ดูแล (ชื่อและอีเมล), บทบาท (ป้าย Superadmin หรือคำว่า Admin), สาขาที่ดูแล (super admin → "ทุกสาขา" · admin → ชื่อสาขา ไม่พบ → ขีด), ปุ่ม "แก้ไข" และไอคอนลบ
- ไม่มีไอคอนลบในแถว super admin และแถวของตัวเอง
- กล่องเพิ่มหรือแก้ไขผู้ดูแล (ฟอร์มเดียวกัน)
  - ตรวจก่อนส่ง: ชื่อหรือนามสกุลว่าง · เบอร์ถ้ากรอกต้องตรงกติกาเดียวกับระบบหลังบ้าน · อีเมลบังคับเฉพาะตอนเพิ่ม · ต้องเลือกสาขาเมื่อเป้าหมายไม่ใช่ super admin
  - เลือกสาขาได้ทีละ 1 · สาขาที่มีผู้ดูแลคนอื่นแล้วถูกปิดพร้อมบอกชื่อคนดูแล (สาขาของคนที่กำลังแก้ยังเลือกได้) · ทุกสาขามีคนดูแลครบ → ปุ่มบันทึกใช้ไม่ได้ และขึ้นว่า "ทุกสาขามีผู้ดูแลครบแล้ว ต้องย้ายหรือลบผู้ดูแลเดิมออกก่อนจึงจะเพิ่มคนใหม่ได้"
  - เป้าหมายเป็น super admin → ซ่อนตัวเลือกสาขาและไม่ส่งสาขาไป
  - ตอนแก้ไข ช่องอีเมลแก้ไม่ได้
  - ตอนเพิ่มส่งอีเมล ชื่อ นามสกุล เบอร์ สาขา · ตอนแก้ส่งชื่อ นามสกุล เบอร์ และสาขา (ถ้าไม่ใช่ super admin)
  - ข้อมูลไม่ถูกต้อง → ข้อความใต้ช่อง (เช่นอีเมลซ้ำ สาขามีผู้ดูแลแล้ว) · ข้อผิดพลาดอื่น → แถบบนกล่อง · สำเร็จ → ปิดกล่องแล้วโหลดตารางใหม่
  - ปิดกล่องได้ด้วยคลิกนอกกล่อง ปุ่ม Esc หรือปุ่ม X
- [ช่องว่าง] หน้าแก้ไขไม่มีช่องระงับบัญชีและตั้งรหัสผ่านใหม่ → ทำสองอย่างนี้จากหน้าเว็บไม่ได้ทั้งที่ระบบหลังบ้านรองรับ (AC-18) · ตารางไม่แสดงว่าใครถูกระงับอยู่
- กล่องยืนยันการลบ "ต้องการลบบัญชีของ (ชื่อ) (อีเมล) ใช่หรือไม่?" → ลบสำเร็จ → โหลดตารางใหม่ · ผิดพลาด → แสดงในกล่อง
- [ช่องว่าง] ข้อความยืนยันเขียนว่า "บัญชีจะถูกลบออกจากระบบถาวรและกู้คืนไม่ได้" และคอมเมนต์ในโค้ดอ้างว่าลบถาวร แต่ระบบหลังบ้านปัจจุบันลบแบบเก็บแถวไว้ (AC-18)

## ค่าตั้งค่าที่มีผลกับพฤติกรรม
- โหมดการทำงาน ค่าเริ่มต้น development · production → log แบบ JSON และค่ายืนยันการล็อกอินผ่าน Google/Facebook ตั้งให้ปลอดภัย
- ที่อยู่ฐานข้อมูลและรหัสลับของ token บังคับ (รหัสลับอย่างน้อย 32 ตัว) ไม่งั้นระบบไม่ยอมเริ่ม
- อายุ access token 30 นาที อายุ refresh token 30 วัน ความแรงของการเข้ารหัสรหัสผ่าน 12
- โฟลเดอร์เก็บไฟล์ค่าเริ่มต้น ./uploads (สร้างให้ถ้าไม่มี) · เพดานขนาดไฟล์ 5MB
- ที่อยู่สาธารณะของ backend ค่าเริ่มต้น localhost:8080 ใช้สร้างลิงก์รูป สลิป และที่อยู่ที่ Google/Facebook ส่งผู้ใช้กลับมา
- โดเมนหน้าเว็บที่อนุญาต ค่าเริ่มต้น localhost:3000 และ localhost:5173
- proxy ที่เชื่อถือ ค่าเริ่มต้นว่าง ค่าที่ไม่ใช่ IP หรือช่วง IP → ระบบไม่ยอมเริ่ม
- รหัสตั้งต้นของ seed ค่าเริ่มต้น Wisetsuk!2026 · รหัสตั้งต้นของผู้ดูแลใหม่ ไม่ตั้งใช้ค่าเดียวกับ seed
- รหัสของ Google และ Facebook ค่าเริ่มต้นว่าง ตั้งไม่ครบคู่ → เจ้านั้นปิด
- หน้าเว็บที่รับผลการล็อกอินผ่าน Google/Facebook ค่าเริ่มต้น localhost:3000/auth/callback
- ค่าตัวเลขที่อ่านไม่ออกหรือว่าง → ใช้ค่าเริ่มต้นเงียบ ๆ
- docker compose ไม่ส่งค่าความแรงการเข้ารหัส รหัสตั้งต้นของผู้ดูแล และการตั้งค่าการเชื่อมต่อฐานข้อมูลเข้า backend → ใช้ค่าเริ่มต้นเสมอ
- หน้าเว็บมีค่าตั้งเดียวคือที่อยู่ของระบบหลังบ้าน
